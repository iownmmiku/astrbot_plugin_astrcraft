# Astrcraft 独立审查：首次接触项目的视角

审查日期：2026-10-09。基线：v1.3.2，提交 `3cf4507e6dc3662c78f690ef9219a813e7ac871a`。

后续状态：F01–F07 的已复现问题已完成源码修复和离线验证，具体变化、初跑与复测结果和未覆盖边界见 [2026-10-11 修复记录](UPDATE_2026-10-11.md)。以下保留审查时的基线发现与证据。

本轮重新阅读安装说明、公开配置和当前实现，从使用者与维护者的视角检查项目。没有沿用历史修复结论，也没有将此前附件中另一个插件的审查意见套用到 Astrcraft。

本轮未修改生产代码、未提交或推送。运行了四个隔离复现脚本：生存与目标、聊天与控制、记忆存储、真实本地管道背压。模拟了模型/游戏边界，没有请求真实模型或连接 Minecraft；这些结果不能用作长时间实服生存成绩。

## 总体判断

项目已经具备较完整的动作、基地、补给、返程、记忆和控制台能力。首次接触项目时，最需要改善的是以下三件事：

1. **生存策略能够在资源耗尽后继续推进。** 当前仍有等待条件无法自行满足的情形，可再生食物也缺少从零建立的完整流程。
2. **行为与报告能够互相对应。** 目标完成、欲望满足、主人控制和普通聊天需要有明确边界。
3. **持续运行与升级有可靠依据。** 记忆存档要能承受坏记录和中断，通信超时要覆盖整个调用，长期自主能力要有可重复的验收成绩。

README 已明确说明长期自主生存尚未充分验证，这个说明是准确且必要的。现有专项通过，仍不能推导出“自然世界里无人干预长期生存”的成功率。

## 已复现的问题

优先级含义：P1 应优先解决，会破坏生存、任务可靠性或持久数据；P2 是明确的边界缺陷，但当前复现条件较窄或影响更间接。

### F01 · P1：低血量断粮后，等待恢复没有出口

- **触发条件：** 白天，血量 6、饱食 0，无食材、附近动物或基地补给，只有一把石镐。
- **当前结果：** 顾问推荐 `cook_food`；生活循环判定需要外出且血量过低，反复等待“天亮和身体恢复”。等待标记又阻止后续计划或模型决策。
- **证据：** 离线连续三轮均为 `step=None`、相同等待理由。断粮时无法靠自然回血满足这个等待条件；外部赠物等事件可以改变状态，但当前策略没有自己的退出路径。
- **位置：** `advisor.py:238`；`life.py:1406`；`life.py:1729`。
- **建议：** 等待前检查恢复所需的食物、饱食与安全条件。无恢复来源时进入有期限的应急取食或重新决策，按距离、风险和成功概率挑选候选，不能无限沿用同一等待理由。

### F02 · P1：普通玩家闲聊会取消采矿返程

- **触发条件：** `in_game_actions=false`，并且 `reply_in_game=false`，或者消息没有触发唤醒。机器人正在保留采矿返程责任。
- **当前结果：** 任意非机器人玩家的消息仍调用 `note_owner_said`，以 `owner` 类型入队；该入口立即清除旧采矿返程计划。
- **证据：** 玩家说 `hello everyone`，在没有模型调用的情况下，返程状态就被清除。随后模型是否执行聊天中的动作另有条件，不影响这个确定的中断结果。
- **位置：** `_conf_schema.json:147`；`main.py:1473`；`life_render.py:127`；`life.py:605`、`life.py:2518`。
- **建议：** 将旁听聊天与控制输入分开。关闭游戏动作时，普通聊天不能进入主人指令通道；只有符合配置与授权规则的明确控制输入才能替换计划。

### F03 · P1：关键步骤失败，长期目标仍报告完成

- **触发条件：** 目标走 LLM 规划路径，第一步成功，后续核心步骤失败。
- **当前结果：** 只有第一步被标为必需，其余步骤重试失败后均可跳过；走到计划末尾就发出 `goal.done`。
- **证据：** 模拟计划“砍树 → 建蓝图”，砍树成功，建蓝图连续失败两次，最终状态仍为 `done`。
- **位置：** `goals.py:603`；`goals.py:431`；`goals.py:440`。
- **建议：** 默认把实现目标所需的步骤标为必需，仅明确的附加工作可跳过。目标末尾还应验证总库存、建筑实际状态等成果，提供“部分完成/失败”的结果，不能以步骤遍历结束代替目标达成。

### F04 · P1：单条坏记忆或保存中断可以造成整库丢失

- **触发条件：** 一条记忆字段非法，或者直接覆盖文件时写入中断。
- **当前结果：** 整批加载失败后从空库开始；正常卸载的强制保存会进一步把空库覆盖到磁盘。直接写原文件也没有保留上一次完整版本。
- **证据：** 两条合法记录加一条 `at="broken"`，加载结果为 0 条，强制保存后原档变成 `entries=[]`。另一次注入截断后写入失败，重启也加载为 0 条。
- **位置：** `memory.py:153`、`memory.py:166`、`memory.py:182`；`main.py:403`。
- **建议：** 逐条校验并隔离坏记录，保存采用同目录临时文件及原子替换。保留坏档与最近有效备份；恢复失败时禁止将空状态自动覆盖到原档。

### F05 · P2：记忆归并没有包含世界归属

- **触发条件：** 不同服务器/维度的同类记录，归一化文本相同，且调用方提供了世界 context。
- **当前结果：** 新 context 覆盖旧 context，但条目 text 仍保留旧原文；检索的归属与内容不一致。
- **证据：** A 服务器的 `supply cache (10,64,10)` 与 B 的 `(900,64,900)` 合为一条；A 检索为空，B 返回 A 的原文，重启后仍如此。新坐标存在 evidence 中，没有被完全删除。
- **位置：** `memory.py:228`、`memory.py:298`、`memory.py:319`。
- **边界：** 这是已复现的 MemoryStore 契约问题，未确认常用生产入口会自动写入这一类带 server 的坐标记录。部分生产死亡/见闻记录只提供 position 或 dimension，世界归属也需要统一。独立地点知识库不能与这项经历记忆问题混为一谈。
- **建议：** 明确哪些记忆允许跨世界共享，其余记录的归并键包含 server/dimension。坐标经历的 text、context 与 evidence 必须维持一致归属。

### F06 · P2：RPC 超时没有覆盖管道写入

- **触发条件：** 引擎不读取 stdin，写缓冲区受到背压。
- **当前结果：** `stdin.drain()` 在超时范围外；请求只有完成写入后才开始等响应的超时。普通监管 ping 也可以一起停在写入阶段。
- **证据：** 本地 Node 子进程不读 stdin，以 2 MB 消息强制填满管道，随后发送普通小 ping。两者超时配置均为 0.05 秒，0.313 秒后仍未完成。
- **边界：** 2 MB 用于故障注入，不代表普通 ping 的大小，也没有证明正常负载经常填满管道。该实测证明的是总调用时限不能得到保证。
- **位置：** `bridge_client.py:401`、`bridge_client.py:407`。
- **建议：** 总超时覆盖写入与等待响应，并限制单请求大小/排队量；超时及取消均清理 pending。监管恢复不应依赖一个已经无限等待的写入调用。

### F07 · P2：动作未开始，探索欲望已经被满足

- **触发条件：** 引擎拒绝提交动作，生活循环捕获异常。
- **当前结果：** 已记录失败，随后仍无条件调用 `note_activity` 满足对应欲望。
- **证据：** 探索动作提交直接抛错，实际 `DriveSystem` 的探索水位却从 0.7 降到 0。
- **位置：** `life.py:2769`、`life.py:2786`；`drives.py:262`。
- **建议：** 区分“想做、尝试、开始、完成”。失败只记录尝试；满足欲望应依据对应活动的真实成果，而不是提交动作或生成总结。

## 需要结合宿主策略确认的控制问题

### C01 · 管理员命令和 LLM 工具的权限约定不一致

目标、暂停、继续命令有 ADMIN 装饰；同类 `mc_set_goal`、`mc_goal_pause`、`mc_goal_resume` 工具没有插件内的身份检查。假非管理员事件调用工具时，确实到达替换目标和恢复自主行动的共享入口。

**实际风险有条件：** 宿主将这些 LLM 工具开放给普通聊天用户，且模型选择调用时，用户可能替换主人目标或恢复暂停。本轮未启动 AstrBot 验证调度层的额外限制，因此不能称为无条件权限漏洞。

位置：`main.py:2212`、`main.py:2253`、`main.py:2297`；`llm_tools_skills.py:492`、`llm_tools_skills.py:526`、`llm_tools_skills.py:534`。

建议把权限判断放在共享控制入口，并明确 AstrBot 管理员、Minecraft 主人、普通玩家分别能做什么。命令、工具和控制台遵循同一规则。

### C02 · “暂停行动”的文字比实际语义更宽

代码与命令回执描述的是“暂停目标和自主行动”，暂停后新的人工动作仍可提交。离线测试中，自主层保持暂停，另一玩家的跟随工具仍提交了 `move.follow`。

这符合仅冻结自主层的实现，**不作为无条件暂停缺陷**。但控制台按钮写“暂停行动”，首次使用者容易理解为身体全部冻结。

建议按钮明确写“暂停自主行动”，同时说明急停的作用。若产品要求主人暂停后排除其他玩家接管，再增加统一的主人控制锁。

位置：`main.py:2255`、`main.py:2269`；`game_agent.py:196`；`pages/control/index.html:67`。

## 从用户体验与自主生存出发的改进

### I01 · 建立可再生食物生产与库存预算

已有成熟作物检查、收割、补种和补种验收，这是有用的基础。但目前主要维护找到的现成农田；未发现从零选址、耕地、引水、记录田地、按成熟周期维护的完整策略。默认储存保护也没有为小麦/甜菜种子设定留种预算。

建议形成“食物预警 → 保留种子 → 建田 → 收割补种 → 加工 → 储备”的长期流程。按预计行程预留口粮，按作物类型保留扩田材料，不能等饱食降低后才开始找食物。

证据：`engine/skills/wood.js:53`、`engine/skills/wood.js:67`、`engine/skills/wood.js:145`；`engine/skills/gathering.js:473`。应表述为缺少完整生产闭环，不能概括成“不会种植”。

### I02 · 为“自主、聪明、流畅”建立可重复的验收标准

已有真实模型持续生存评测入口，能汇总死亡、饥饿、停滞、任务衔接和模型消耗；README 也披露本轮没有真实模型长时间成绩。下一步需要固定最低可接受结果，而不仅是脚本运行结束。

建议先定义一个基础生存档：自然世界、空背包、多种子、多个昼夜、记录所有人工干预。验收至少覆盖木材与工具、可持续食物、安全住处及库存增长，再比较死亡、饥饿时长、重复失败、无进展时长、动作衔接的 P95 延迟和模型成本。先建立基线，再谈优化带来了多少改善。

无需把任意站立不动都判为卡住；原地合成、熔炼等正常工作应与失败结合判断。现有 `completed` 仅表示测量完成，应继续保留这个准确语义。

### I03 · 统一首次安装路径与启动诊断

首次安装涉及 AstrBot、Node、npm、服务器、模型和 Pages，用户很难判断失败在哪一层。目前文档还有具体漂移：

- `docs/SETUP.md:67` 的外置引擎复制命令没有复制 `pages/` 与 `.astrbot-plugin/`，照做不会得到 README 介绍的原生控制台资源。
- `docs/SETUP.md:162` 写 `engine/config/bot.config.json`，默认实现读取插件根目录的 `config/bot.config.json`（`engine/config.js:197`）。认证缓存说明同样需要区分配置路径与默认路径。
- `.gitignore` 没有排除 `config/auth-cache/`。这是凭据误提交的防护缺口，不代表现有仓库已经泄露凭据。
- README 使用 `npm ci`，部署说明的另一入口使用 `npm install`。两份说明应围绕同一安装结果组织。

建议只保留一套主安装流程，外置引擎作为明确分支；提供一次诊断输出，分别检查 Node 版本、锁定依赖、引擎通道、服务器连接、模型工具能力与 Pages 支持。每一层都给出可操作的失败提示。

### I04 · 让可选观战真正降低安装成本

观战模块已经采用延迟加载，但依赖层面仍不是最小安装：`engine/package.json` 的 `canvas` 是必装依赖，观战相关 optionalDependencies 在默认 npm 安装中也会安装。npm 的“optional”表示安装失败可以继续，省略安装需要显式使用 `--omit=optional`，见 [npm 官方说明](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/#optionaldependencies)。

建议评估把仅供观战的依赖移到可选扩展，并在文档中区分最小游戏引擎与完整观战安装。本轮没有测量全新安装耗时或包体，不能据此给出具体性能收益。

### I05 · 让等待理由说明“接下来如何恢复”

控制台已经显示意图、活动和等待理由，不需要再增加重复信息。可以把理由进一步结构化：当前阻碍、下一次尝试时间、退出条件、已试策略、真实任务进展和本轮模型消耗。

这样用户能区分正在正常休息、缺料等待、重试冷却与无出口停滞，也更容易提供有效 Issue。仅显示“等待身体恢复”无法解释恢复来源是否存在。

### I06 · 收拢控制与存储约定，接入基础 CI

主入口、生活循环与引擎主体均较大，多个布尔状态同时控制暂停、目标、模型和应急恢复。建议围绕现有模块逐步建立统一的身体控制状态及授权入口，明确谁能替换计划、谁能恢复行动，并保留被中断任务的责任。

记忆、知识、插话队列和工作站存档也应共享版本、校验、原子保存、坏档保留的约定。其他存储本轮只读检查，未做写入中断实测，不能笼统宣称都已损坏。

已有回归脚本可以接入轻量 CI，先自动运行离线契约检查，再单独安排真实服务器专项。当前提交没有 `.github` 工作流。应优先加入上述失败情形和端到端成果验收，减少依赖人工逐次运行与记忆。

## 建议实施顺序

1. **修生存与控制中断：** F01、F02，以及共享控制入口的权限约定。先保证不会无限等待，也不会因普通闲聊遗失退路。
2. **修成果与数据可靠性：** F03、F04、F05、F06、F07。让“完成”和“满足”有实际依据，重启与故障不丢重要状态。
3. **补长期生存流程：** 建田、留种、口粮预算、库存预警，并完善等待的退出条件。
4. **完成验收与交付：** 多种子真实模型长时评测；同步修正文档、最小依赖安装、诊断和 CI。文档与基础 CI 可以并行推进。
