# 长期目标的控制与暂停恢复

目标规划可能等待模型响应。每个请求都有独立世代：新目标、暂停、急停、放弃、主动退服和卸载会先使旧规划失效，再等待引擎操作。支持取消的模型请求同时被取消；即使模型不响应取消，迟到的计划也不能覆盖新目标或创建第二个执行循环。暂停后再继续、退服后立即重连，也不会重新激活旧规划。

正在执行的目标由单个循环推进。暂停会停止当前引擎动作，保持步骤位置，把本次中断从失败重试预算中扣除；重复暂停不会让一个只允许一次尝试的步骤失败。若服务端在取消到达前已经完成动作，恢复时先读取原任务结果和验收条件，避免重复执行已完成的合成等操作。验收条件失败时，技能返回的 `ok: true` 不能覆盖验收结果。

砍树、采矿、挖建材可恢复原引擎任务的采集检查点，保留库存基线、追加数量、子步骤检查点和矿口。通用 `collect` 的数量是库存总目标，恢复时按这个目标补缺；其合成、狩猎等分支仍依赖实际库存或世界状态检查，不宣称能精确重放任意副作用。恢复后的实际库存须达到原目标，采矿仍须通过安全返程验收，已获得的数量不会再算成一整批新需求。

`collect` 的直接采集分支保存最初的子技能数量与路线选择，暂停后不因缺口变化而丢失子检查点。即使已经采足库存总目标，也继续原采矿检查点以完成返程；不会因为数量达标就在坑里报告完成。

## 内部 RPC

`skill.run` 保留原有请求格式，并接受可选的外层字段 `resume_task_id`：

```json
{
  "skill": "mine_ores",
  "params": {"ore": "coal", "count": 8},
  "resume_task_id": "原先被暂停并取消的任务 ID"
}
```

它供 GoalManager 恢复任务使用，不加入模型技能参数目录或用户配置。引擎只接受自己保存的、状态为 `cancelled` 的最近采集任务；技能和参数必须完全相同，机器人对象、实体、连接、身体世代和维度也必须保持相同。死亡、重生、换服、换维度、连接已断开或被使用过的恢复引用都会被拒绝。检查点从引擎内存复制，调用方不能提交任意检查点数据，迟到的旧协程也不能修改新执行的副本。

恢复失败后不会退回普通 `skill.run` 再采一整批；目标停止并报告原因，随后重新观察当前状态。没有提供该字段的既有工具、客户端和技能参数保持兼容。

## 验证

- `dev-tools/test_goal_control.py`：实际 GoalManager 和插件控制入口，覆盖迟到规划、新指令、退服后重连、连续暂停、提交途中暂停、恢复引用失效、失败预算及验收条件。
- `dev-tools/test_goal_resume.js`：实际引擎、任务队列和采集技能，模拟 Minecraft I/O，验证已有 5 个物品时追加 8 个的原目标、暂停后剩余采集、最后一个掉落后暂停、建材计数、旧检查点隔离及身体边界。
- `dev-tools/test_goal_resume_live.py`：本机 Paper、实际物品和技能。机器人已有 5 煤，执行追加 8 煤的目标，中途人工暂停两次；最终必须恰好 13 煤，且安全返程通过。只修改隔离测试场地和随机测试账号，无模型调用，不修改全局时间、难度或游戏规则。

这些回归验证控制和执行语义，不代替真实模型的长期开放世界生存评测。
