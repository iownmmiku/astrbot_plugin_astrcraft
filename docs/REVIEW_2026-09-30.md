# Astrcraft 项目检查报告

检查日期：2026-09-30。检查基线：`7ab5271`，插件版本 1.1.0。以下保留修复前的检查结果与行号；后续实现修改和验证见 [修复记录](REPAIR_2026-09-30.md)。

范围包括 Python 自主循环、聊天代理与工具接口，以及 Node 动作、任务队列和生存反射。以下问题通过调用仓库实际模块、模拟游戏接口或时间进行最小复现；服务器网络时序和游戏动作最终结果未做真服验证。

P1 表示应优先修复的自主行动、控制或生存问题；P2 表示特定功能或测试可靠性问题。

## 1. [P1] 决策出错两次后，BLOCKED 无法自行恢复

- 位置：[life.py:710](D:/工作台/Astrcraft/life.py:710)、[life.py:836](D:/工作台/Astrcraft/life.py:836)、[life.py:844](D:/工作台/Astrcraft/life.py:844)。
- 触发：自主行动连续两次异常，或决策连续超时两次，调用 `note_blocked()`。
- 原因：后续循环在 `current_hold() != NONE` 时直接跳过决策；解除 BLOCKED 的代码却只在决策成功后执行。没有独立的模型恢复探测入口。
- 复现：让实际 `_loop()` 的动作代理连续抛出两次临时异常，然后恢复代理并调用 `resume()`、`wake()`，模型调用次数仍为 2，停牌仍为 `blocked`。
- 影响：一次短暂故障即可让机器人长期不再自主行动；恢复模型连接也无效。
- 修复方向：给 BLOCKED 独立的恢复探测或明确的解除入口，避免用被停牌阻止的决策来解除停牌。

## 2. [P1] 30 秒失败退避会不断续期，停住约半小时

- 位置：[life.py:375](D:/工作台/Astrcraft/life.py:375)、[life.py:692](D:/工作台/Astrcraft/life.py:692)。失败统计窗口在 [life.py:174](D:/工作台/Astrcraft/life.py:174)。
- 触发：同一技能在半小时内失败三次。
- 原因：退避到期后仍使用同一批失败记录，再设置一次 `now + 30`；统计记录没有被消费，也没有允许一次重新规划。
- 复现：三个失败时间均为 1000；在 t=1000 返回 True、期限 1030，t=1031 又返回 True、期限 1061，t=1200 仍返回 True；失败记录超过半小时窗口后才允许通过。
- 影响：阻止整个自主循环，连更换技能、处理新输入和自动解除暂停都无法进入。
- 修复方向：对每批新增失败只触发一次退避，或者只限制失败技能，退避结束后允许重新决策。

## 3. [P1] 取消挖掘只停止等待，底层挖掘仍继续

- 位置：[engine/actions.js:172](D:/工作台/Astrcraft/engine/actions.js:172)、[engine/actions.js:2283](D:/工作台/Astrcraft/engine/actions.js:2283)。
- 触发：挖掘期间取消任务、急停、抢占或等待超时。
- 原因：`Promise.race()` 让动作包装器提前退出，但没有调用 mineflayer 的 `stopDigging()`。引擎的 `cancelAll()` 也只清理移动控制。
- 复现：调用实际 `Actions.dig()`，20ms 后 abort，包装器返回 `CancelledError`；模拟底层挖掘在 50ms 后仍改变方块，`stopDigging` 调用次数为 0。
- 影响：任务显示已取消，身体却可能继续挖掘；被抢占的旧动作也可能与新动作重叠。此处未验证服务端最终接受哪些包。
- 修复方向：把取消与超时传递给底层动作，停止挖掘并等待操作收尾后再释放执行权。

## 4. [P1] 溺水反射读取了错误的氧气字段

- 位置：[engine/bot.js:1054](D:/工作台/Astrcraft/engine/bot.js:1054)。
- 原因：代码读取 `bot.entity.oxygenLevel`；仓库安装的 mineflayer 在 `lib/plugins/entities.js:499` 更新的是 `bot.oxygenLevel`。
- 复现：机器人在水中、`bot.oxygenLevel=2`、`bot.entity.oxygenLevel` 未定义；实际 `_reflexTick()` 没有提交“浮上水面换气”。
- 影响：本地溺水自救分支不能正常触发。
- 修复方向：读取当前依赖实际提供的氧气字段，补充低氧状态的反射测试。

## 5. [P1] 防抖分支把同一个任务入队两次并执行两次

- 位置：[engine/goals.js:284](D:/工作台/Astrcraft/engine/goals.js:284)、[engine/goals.js:340](D:/工作台/Astrcraft/engine/goals.js:340)。
- 触发：当前任务刚开始，新的高优先级任务试图抢占，被 `_thrashGuard()` 拦下。
- 原因：防抖分支内部 `push(task)`，随后又走到函数末尾的无条件 `push(task)`。
- 复现：用户任务开始 5ms 后提交 `PRIORITY.CRITICAL` 任务，队列中同一个 task 对象出现两次；释放用户任务后新任务执行两次。统计为 `submitted=2`、`completed=3`。
- 影响：动作重复、完成事件重复、统计失真；同一个任务号可能在完成后再次执行。
- 修复方向：确保每次提交只有一个入队出口，并禁止泵再次执行已完成任务。

## 6. [P1] 空手时，即使背包有食物也无法进食

- 位置：[engine/actions.js:1297](D:/工作台/Astrcraft/engine/actions.js:1297)。
- 触发：`bot.heldItem` 为空，背包里有面包等可用食物。
- 原因：装备食物的判断要求已经持有物品，空手时反而跳过 `equip()`，直接调用 `consume()`。当前 mineflayer 的 `consume()` 会读取 `bot.heldItem.name`。
- 复现：实际 `Actions.eat()` 选中背包面包后失败，装备次数为 0。
- 影响：出生、复活、丢弃手持物品或工具损坏后的常见状态下，自动吃东西失效。
- 修复方向：空手或手持物不是目标食物时，都先装备食物。

## 7. [P1] /mc急停没有暂停生活循环，会再次提交自主动作

- 位置：[main.py:1892](D:/工作台/Astrcraft/main.py:1892)、[engine/index.js:1128](D:/工作台/Astrcraft/engine/index.js:1128)。
- 原因：命令仅取消当前队列并暂停 `GoalManager`，没有暂停独立运行的 `LifeLoop`，也没有持久的急停状态。
- 复现：执行实际 `cmd_stop()` 后，目标系统为 paused，但生活循环仍未暂停。下一轮满足空闲条件时仍可进入自主决策。
- 影响：用户收到“已急停”后，机器人又开始行动。
- 修复方向：在所有主动决策与动作提交入口统一检查急停状态，并提供明确的恢复操作。

## 8. [P2] 饥饿时每 200ms 重复排队吃饭，堆积大量相同任务

- 位置：[engine/bot.js:1112](D:/工作台/Astrcraft/engine/bot.js:1112)、[engine/bot.js:1640](D:/工作台/Astrcraft/engine/bot.js:1640)。
- 触发：长用户任务执行中，饱食度低，背包有食物；普通进食反射不能抢占当前任务。
- 原因：同名去重只检查当前任务，未检查 pending 队列。进食尚未开始时，`_eating` 和 `_lastEatAt` 也不会阻止继续提交。
- 复现：保持同一个用户任务为 current，调用实际反射 tick 十次，pending 中积累十个进食任务。
- 影响：长任务结束后先处理大量陈旧反射，耽误新指令，产生重复进食与报错。
- 修复方向：对排队中的反射按名字或状态去重，并在执行前重新验证是否仍需要。

## 9. [P2] mc_take_items 缺少箱子坐标，已连接时必然失败

- 位置：[llm_tools_core.py:343](D:/工作台/Astrcraft/llm_tools_core.py:343)、[engine/index.js:936](D:/工作台/Astrcraft/engine/index.js:936)。
- 原因：工具只发送 `item` 与 `count`，引擎的 `container.withdraw` 强制要求 `x/y/z`，没有自动选择附近箱子的分支。
- 复现：实际工具发出 `('container.withdraw', {'item': 'bread', 'count': 2})`；这些参数经过 `normalizeCoords()` 时，三个坐标均为 NaN，会被拒绝。
- 影响：专用“从附近箱子取物品”工具无法工作，即使机器人已经站在箱子旁边。带坐标的 `mc_chest(action='take')` 是另一条路径。
- 修复方向：由工具查找目标箱子并传入坐标，或为引擎接口明确实现附近箱子选择。

## 10. [P2] mc_goto(player=...) 实际启动永久跟随

- 位置：[llm_tools_core.py:390](D:/工作台/Astrcraft/llm_tools_core.py:390)、[engine/movement.js:784](D:/工作台/Astrcraft/engine/movement.js:784)。
- 原因：文档区分“到玩家旁边”和“一直跟随”，实现却把前者也发送给 `move.follow`。跟随在到达后继续循环，直到取消或目标持续不可见。
- 复现：调用实际 `mc_goto(player='Alice')`，得到的 RPC 为 `move.follow`。
- 影响：到达玩家身边后任务仍不完成，阻塞后续队列与自主循环。
- 修复方向：给前往玩家提供到达即结束的导航路径，把持续跟随留给 `mc_follow`。

## 11. [P2] 打开 auto_connect 后，手动退服会被监管循环重新连接

- 位置：[main.py:770](D:/工作台/Astrcraft/main.py:770)、[main.py:409](D:/工作台/Astrcraft/main.py:409)。
- 原因：插件只设置 `connected=False`，没有保存用户主动离线意图。引擎虽知道 manual disconnect，Python 监管循环仍把它当作待恢复的掉线。
- 复现：实际 `_do_disconnect()` 返回已退服，随后调用满足冷却条件的 `_supervise_tick()`，连接次数增加 1，`connected` 又变为 True。
- 影响：`/mc退服` 无法保持离线；实际重连时间取决于 20 秒监管周期和 25 秒连接冷却。
- 修复方向：区分主动离线与异常掉线，在用户明确进服前保留离线状态。

## 12. [P2] 攻略读取接口允许越出 skills_docs 读取其他 Markdown

- 位置：[llm_tools_life.py:317](D:/工作台/Astrcraft/llm_tools_life.py:317)、[knowledge.py:139](D:/工作台/Astrcraft/knowledge.py:139)。
- 原因：直接拼接输入路径，没有限制为攻略目录中的已登记名称，也没有检查解析后路径是否仍在目录内。
- 复现：本机调用实际 `mc_load_skill('../readme')`，成功返回插件根目录 README。
- 影响：模型可获得攻略目录以外的 Markdown 文件内容；工具返回的文本会进入模型上下文。实际可访问范围受文件名、系统路径规则和运行账户权限限制。
- 修复方向：只接受已列出的攻略名，并检查解析后的路径位于攻略目录内。

## 13. [P2] 模糊去重把不同矿石、不同工具的教训误删

- 位置：[knowledge.py:161](D:/工作台/Astrcraft/knowledge.py:161)。
- 原因：字符相似度达到 0.35 就拒绝新增，没有保留目标矿石、工具等级等关键事实的差异。
- 复现：先记录“挖铁矿前必须先用石镐，木镐挖不动”，再记录“挖钻石矿前必须先用铁镐，石镐挖不动”；第二条被判为重复，库里仍只有一条。
- 影响：新学到的关键规则被静默丢弃，机器人可能反复犯相同的工具等级错误。
- 修复方向：对近似文本保留关键事实差异，避免仅凭文字相似度判定语义重复。

## 14. [P2] 测试汇总会把超时或无法启动输出为“全部通过”

- 位置：[dev-tools/run_all.py:341](D:/工作台/Astrcraft/dev-tools/run_all.py:341)。
- 原因：`timeout/error` 被归入 `other`，只打印而不参与最终退出码；最终失败判断只检查 `real_fail`。
- 复现：用一个 status 为 timeout 的测试结果运行实际 `main()`，退出码为 0，仍打印“✅ 全部通过”。
- 影响：回归或 CI 可能漏报测试根本没完成的情况。
- 修复方向：超时与启动错误应使总结果非零，并区分通过、跳过、未完成。
