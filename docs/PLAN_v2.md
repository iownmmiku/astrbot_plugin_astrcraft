# Astrcraft 下一步计划（对照 numen 之后的 7 项）

> 来源：读完 numen `1.21.1` 分支的 `AgentLoop` / `EventQueue` / `Run` / `Hold` /
> `GoalSteward` / `Compactor` / `EntityAgentLoop` / `SystemPromptComposer` 之后，
> 逐层对照出来的差距，加上用户新提的"永不空闲"要求。

**前提差异（先说清楚）**：numen 是 Fabric 客户端 mod，进程内、每 tick 同步推进；
Astrcraft 是 Python 插件 + Node 子进程 + NDJSON RPC。所以"每 tick 一个 pump"
抄不过来——我们的等价物是 200ms 反射层 + RPC。下面的方案都是**按我们的架构改写的**，
不是照搬。

## 关于"永不空闲"和"不要乱走乱挖"的冲突（必须先解决的设计问题）

用户要求：**每次没有任务的时候，立即发起一个任务。**
而我上一轮刚加了 `life_min_decide_gap = 6`（承诺机制），用来治"乱走乱挖"——
当时的病因是：`task.finished` 立刻唤醒 → 每几秒重新决策 → **每决策一次就可能改主意**。

**这两件事不矛盾，但必须区分开**：

| | 病 | 药 |
|---|---|---|
| 乱走乱挖 | **重新规划**太频繁（改主意） | 别频繁重规划 |
| 永不空闲 | **手上没活**（站着） | 别停手 |

所以正确的做法**不是**加时间间隔，而是**让"计划"活着**：

1. **有任务在跑** → 等它（不重规划）
2. **计划里还有下一步** → **立刻执行**（0 延迟、不花 token）
3. **计划空了** → **立刻重新规划**（一次决策，**不等 6 秒**）
4. **规划不出任何事** → 记成 `IDLE_NO_WORK` 并**说出来**（可见，不是静默站着）

**结论：`min_decide_gap` 这个"一刀切 6 秒"要拆掉**，换成：
- 计划连续性（第 2 条）承担"不频繁改主意"
- **只对"同一件事反复失败"退避**（失败感知退避），而不是对所有决策退避

这意味着要**改掉我上一轮自己写的东西**（`test_life_rhythm` 的承诺断言要重写）。
先写在这里，免得到时候看起来像"改坏了"。

## W2　停牌表 `Hold`（P0，"她不动"的根治）

**现状**：`_paused` + `_pause_until` + `_busy_until` + `_is_connected()` + `_engine_busy()`
散成 5 个条件，每个都能静默 `continue`。`_auto_resume_if_expired()` 是补丁——
`life.py:373` 的注释自己承认"早期版本只 pause、靠 task.finished 事件 resume"→ 被永久按住。

**改**（照 numen 的 `Hold` + `releasedBy` 表）：
```
NONE              在跑/可以跑
DEAD              她死了            ← 复活解开
DISCONNECTED      没进服            ← 连上解开
PAUSED_BY_OWNER   主人按了暂停      ← 主人恢复 / 超时自动恢复
BLOCKED           模型端点不可用    ← 端点恢复
ENGINE_DOWN       引擎进程没了      ← 引擎起来
IDLE_NO_WORK      能跑但确实没事做  ← 有新输入/新目标
```
- **唯一答案**：`current_hold()` 合成，别处不许再各自判断
- **只在变化沿打日志**（进/出各一条，停牌期间不刷屏）
- `/mc状态` 显示"她为什么没在动"

**验证**：新增 `test_hold.py`——每个状态的进入/释放路径、变化沿只报一次、
`IDLE_NO_WORK` 和"停牌"的区别（前者能跑，后者不能）。

## W3　失败在历史里留痕（P0，治"重复做同一件失败的事"）

numen 三条做法：
1. 失败/切断 → 往历史写**切断点**（"这一轮没连上（原因）"）
2. `ProtocolView` 建下次请求时**回答悬空的工具调用**（"被切断，结果未知"）
3. **每条链只重试一次**（只重试"调用本身出错"；空回复算失败但**不重试**）

**Astrcraft 现状**：决策超时 → 记日志 → `sleep(8)` → 重新决策 ✗ **模型不知道上一轮失败了** ✗

**改**：
- 决策失败/超时 → 历史里写一条切断点
- 超时导致工具调用悬空 → 下次建提示时补"结果未知，别当成没发生"
- 每条链只重试一次，重试过就如实报错

**验证**：新增 `test_agent_trace.py`——切断点进历史、悬空调用被应答、重试只一次。

## W4　输入队列 + 投递方式表（P1，改动最大）

numen 的 `EventQueue` + `EventTypes.Delivery`：**主人的话和世界事件共用一个队列**，
每种类型带投递方式：

| 投递 | 什么时候注入 |
|---|---|
| `STEER` | 一批工具**结算完**、下次调模型**之前** |
| `FOLLOW_UP` | 只在她**本来要停**的时候接上 |
| `CONTROL` | 只在**完全空闲**时执行 |

设计原则（numen 注释原话）：**"排空"是"到点就走"，不是"立刻发出"**——
熟度只读状态、可反复问、答案一致 → **不存在"错过的排空"**，也不需要记"我刚才想排空"。

**Astrcraft 现状**：没有这一层 ✗ 只有 `task.finished → _wake.set()`。
**后果**：她跑长任务时主人说话听不见；世界事件（箱子满、怪来了、工具坏了）只有下一轮才知道。

**改**：
- 一个 `inbox`（主人话 + 引擎事件），`Delivery` 三态
- 上限 200，满了丢最老**并记账**（排空时如实补一句"丢了 N 条"）
- 落盘，跨重启活着
- 引擎侧事件入队：`task.finished` / 受伤 / 饥饿 / 工具坏 / 箱子满

**验证**：新增 `test_inbox.py`——熟度规则、三种投递的注入点、上限丢弃记账、落盘恢复。

**依赖**：W7 的"世界事件唤醒"要用它；但 W7 可以先用"计划连续性"落地，不等 W4。

## W5　记忆是"累积的账"+ 评估窗口从目标设定起算（P1）

numen 两条我认为最值钱的设计：

**① 摘要是累积的账，只能增补、不能反复转述**
`Compactor` 有**两套提示词**：首份用 `COMPACT_PROMPT`（7 段结构、要求坐标逐字保留），
第二次起用 `UPDATE_PROMPT` 把旧摘要**单独给出来**、在它之上更新。原话：

> 不这么做的话，上一份摘要会随着"较早的部分"被再总结一遍——
> **每压缩一轮，三轮前记下的坐标与教训就少一点，而且没人会发现**。

**这直接适用于 `memory.py`**：我的 `consolidate` 是**合并去重**，同类教训会被反复压缩 ✗

**② 评估窗口从"目标设定那一刻"起算**
`GoalSteward.sinceGoalForJudge()` 的真实事故：

> **第一轮挖到 64/128 那条早滚出窗口，后面几轮评估器咬定"没有挖矿证据"，
> 把她赶去满世界找矿四分钟。**

`_clip()` 就是"截最近 N 条" ✗ 同样的坑我们必然也有 ✓

**改**：
- `consolidate` 改成**只增补**：保留首见时间 + 每次的证据，不改写已有描述
- 压缩时把"上一份"单独给出来，要求**在它之上更新**、明令"旧信息一条不许丢"
- 目标评估的窗口**从目标设定那条消息起算**，字数封顶兜底

**验证**：新增 `test_memory_ledger.py`——模拟多轮合并，断言坐标/数字/教训**一个都不丢**。

## W6　Token 台账 + 缓存命中率（P2）

numen：`TokenLedger` 跨会话、四元用量（↑↓ 读写缓存）、**上一轮**的命中率
（"累计命中率会被历史稀释，看不出刚才那轮打穿了缓存"）、`CacheWaste` 诊断。

**Astrcraft 现状**：完全没有 ✗ 我不知道一次决策花多少 token、缓存有没有生效 ✓
而"不烧 token"（W4 的前提）需要这个数据。

**改**：
- 记每次调用的用量（含缓存命中/写入）
- 显示**上一轮**命中率，不是累计
- `/mc状态` + 日志可见

**验证**：新增 `test_tokens.py`——四元累加、上一轮 vs 累计、缺字段不炸。

## W7　永不空闲（P0，用户新要求）

见上面"关于冲突"那节的状态机。要点：

1. **计划连续性**：`_pop_plan_step()` 有下一步 → **立刻执行**（0 延迟、不花 token）
2. **计划空了 → 立刻重规划**（拆掉 6 秒一刀切）
3. **失败感知退避**：只对"同一件事反复失败"退避（复用引擎已有的
   "这已经是第 N 次"计数），不对所有决策退避
4. **`IDLE_NO_WORK` 要可见**：确实没事做时，记进状态并说出来，不静默站着
5. 和 W2 的 `Hold` 对齐：`IDLE_NO_WORK` 是"能跑但没事"，不是停牌

**验证**：
- 新增 `test_never_idle.py`——计划有步骤时**不调模型**直接执行；计划空了**立刻**决策；
  反复失败时才退避
- **重写 `test_life_rhythm.py` 的承诺断言**（上一轮那两条要按新契约改）

## 明确不做的

- **照搬 numen 的进程内 pump**：架构不同，做不到；我们的等价物是 200ms 反射层
- **多同伴（每实体一个 loop）**：产品范围问题，不是能力差距，除非你要
- **MCP 外接大脑 / 语音 / 打字机气泡**：功能，不是能力
- **为"永不空闲"而无限调模型**：那正是用户之前抱怨的"无意义的动作"。
  空闲时必须优先用**不花 token 的路**（计划 → 目标 → 才轮到决策）
