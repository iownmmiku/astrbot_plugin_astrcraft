## C4. 第四轮：合成可靠性，以及"我自己的修复反而是 bug"

### 最重要的发现：主动心跳在干扰合成

第二轮为了修"熔炼时静默 40 秒被服务端判失联"，我把心跳改成**无条件发送** `bot.look()`。
它确实治好了掉线，但**引入了合成偶发失败**：`bot.look` 会改动本地实体状态
（yaw/pitch/onGround），插进容器窗口事务中间会扰动服务端的点击确认——
而 1.17+ 服务端**只在它认为客户端状态过期时才回应点击，被忽略的点击毫无回报**，
mineflayer 的合成却完全依赖点击落点（它还会在本地伪造产出格内容）。

**对照实验（每种 5 次）**：

| 心跳配置 | crafttest 完全通过 |
|---|---|
| `bot.look()` 无条件发送（第二轮的"修复"） | 3/5 |
| 心跳完全关闭 | **5/5** |
| 裸 look 包无条件发送 | 4/5 |
| **裸 look 包 + 仅空闲时发送（最终方案）** | **5/6** |

**关键验证**：心跳完全关闭时，"挖矿 → 熔炼（静默 43 秒）→ 做铁镐"依然 **13/13 全过**——
说明长时间静默靠**客户端超时放宽到 180 秒**就够了，主动心跳从来不是必需品。

### 同时修掉的真问题

| # | 问题 | 修法 | 验证 |
|---|---|---|---|
| F1 | **错误翻译把一切 timeout 都说成"寻路超时"** | `humanizeError` 里 `includes('timeout')` 命中一切超时，连合成超时都被报成寻路问题、还建议"拆成几段短距离移动"——把排查方向彻底带偏 | ✅ 只在消息同时含 `path` 时才判寻路 |
| F2 | 2×2 合成格残留材料 | 玩家自己的 2×2 格是**持久**的，关窗不清空；残留 1 块木板时服务端算出的产物是**按钮**，本地却以为在做镐子 | ✅ 每次合成前清格；背包里不再出现莫名的 `oak_button` |
| F3 | 多产出配方材料算错 | 按"单批消耗 × 件数"算，而 stick 一批出 4 个 → 要 4 根木棍被算成需要 8 块木板 | ✅ 改为按批数算 `ceil(件数 / 每批产出)` |
| F4 | 首次合成"没有产出"直接报错 | 点击被忽略时 mineflayer"成功返回但什么都没做" | ✅ 3 轮复位重试（关窗 → 等待 → 同步 → 清格） |
| F5 | 合成结果停在窗口里 | "任务完成"与"背包里真的有"存在时间差，外部观察者读到矛盾结果 | ✅ 主动关窗 + 收敛等待 |
| F6 | 窗口状态不同步 | 用 mineflayer 官方 `_syncWindow` 复位；**顺序必须是"同步 → 清格 → 再同步 → 合成"**（清理本身也点击，会推进 stateId） | ✅ 复位次数从"每次必失败"降到多数运行 0 次 |

### 自我修正：一次"测试环境"误判

排查中我一度归因于"世界被挖脏"和"服务器退化"，实际主因是 F1-F6 与心跳干扰。
唯一站得住的环境结论：**传送到未生成的冷区块时，服务端生成地形会静默忽略点击**——
所以测试现在用 `fill` 在固定坐标重建确定性竞技场，而不是传送到远处。

### 遗留问题（如实记录）

`crafttest` 6 次抽样中 **5 次完全通过**，失败集中在**合成工作台**这一步
（4 个物品的 2×2 配方，点击次数最多、最容易踩到状态漂移）。
失败时引擎**如实报错**（"合成没有产出"），不会假装成功——
测试里"报告与实际一致"这条断言**每次都通过**。

对比：真实能力链 **B13（挖矿→熔炼→铁镐）稳定 13/13 全过**。

## C5. 第五轮：AstrBot 集成层的三个"静默失败"

这一轮的教训是：**引擎层全绿 ≠ 插件在 AstrBot 里能用**。
前四轮的验证都停留在"引擎能力"和"插件静态契约"，
而真正卡住用户的是 AstrBot 的加载与调用约定。

| # | 症状 | 真因 | 修法 |
|---|---|---|---|
| X1 | **所有工具调用失败**：`tool_mc_goto() missing 1 required positional argument: 'event'` | AstrBot 的绑定生命周期按 `__module__ == 插件主模块路径` 过滤 handler，只绑定定义在主模块里的工具。本插件的工具都在 `llm_tools_*.py` 子模块里，**永远匹配不上**，于是 handler 保持未绑定的原始函数——AstrBot 调 `handler(event)` 时 event 被当成 `self`。**39 个工具（QQ + 游戏内）全部不可用** | `main.py` 新增 `_bind_llm_tools()`：自己把工具绑定到实例。三重保证：`@filter.on_astrbot_loaded()` 钩子 + 延迟 5/15/40 秒补绑 + 调用时兜底绑定 |
| X2 | 绑定改好了，但**技能类工具仍全部失败**：`object async_generator can't be used in 'await' expression` | `_submit_skill` 写成带 `yield` 的 async generator，而 10 个技能工具都是 `return await self._submit_skill(...)`——**await 一个 async generator 必然抛错**。这个错误只在运行到该行时才炸，注册/签名/加载测试一律发现不了 | 把 `_submit_skill` 改成普通协程（`return` 代替 `yield`），10 个调用点无需改动。新增静态检查 `bot/tools/check_await.py` 防止复发 |
| X3 | **过日子循环启动了却一次决策都没做** | ① `decide()` 没有超时，LLM 一旦卡住整个循环永久冻结且不留日志；② 游戏内代理在工具失败时也 `life.pause()`，而恢复依赖 `task.finished`——工具失败不产生任务，于是**永久停滞** | 决策加 90 秒超时；`pause()` 带 10 分钟自动恢复期限；只有工具**真正成功**时才暂停 |

**验证方式（都是新增的）**：

- `bot/tools/test_tool_binding.py`：用**真实 FunctionToolManager + 真实时序**复刻线上故障（先注册未绑定函数 → 再 initialize），断言绑定被修好，且**两条调用路径**（我们自己的 + AstrBot 的）都能执行；并**逐个真实调用全部 34 个工具**，抓"运行时才炸"的类型错误 —— **15/15 通过**
- `bot/tools/check_await.py`：静态排查"被 await 的 async generator"，10 处全部修复

**为什么之前几轮的测试没发现**：`test_game_agent.py` 用的是自己造的假 handler（闭包，已绑定），
跟真实注册方式不同；而"工具执行"这条路径从来没被端到端验证过。
**教训**：验证必须走真实链路，假对象只能验证逻辑，验证不了集成约定。

**另一个教训**：改完代码要确认**运行中的进程真的加载了新代码**。
用户重载插件后仍在跑旧代码（日志行号可证），原因是 `__pycache__` 的旧字节码——
所以每次同步后都会清掉它。

## C6. 第六轮：全面优化（阻塞、死代码、度量）

这一轮不再"发现一个修一个"，而是**系统性度量 + 一次性排查同类问题**。

### 先加度量：事件循环阻塞监控

Node 是单线程的，任何同步耗时操作都会让引擎"短暂失联"——RPC 收不到也回不了，
用户感受就是"她在干活时你问不到状态、急停也没反应"。
所以在 `bot.js` 加了一个 250ms 的循环延迟监控，**阻塞超过 1.5 秒就告警，
并把当时正在跑的任务名一起记下来**。有了它，阻塞源直接暴露在日志里，不用再猜。

## C7. 第七轮：让"主动生存"真正跑通

起点是一句直接的质问：**"她会主动生存吗，如果我什么都不说？"**
答案是：她会主动尝试，但**几乎每次都失败**。她自己的记忆文件（126 条，其中 106 条是任务结果）
给出了铁证——连续几十分钟重复同三条失败：

```
「挖石头」连续多次没有进展
「做工具」挖圆石失败：连续多次没有进展
「建庇护所」材料凑不齐（需要圆石/泥土/木板…还要火把和门）
```

### 根因：一行被误用的 API 锁死了整条生存链

```js
// mineflayer 的真实实现（lib/plugins/digging.js）
function canDigBlock (block) {
  return block.diggable &&
         block.position.offset(.5,.5,.5).distanceTo(bot.entity.position.offset(0,1.65,0)) <= 5.1
}
```

它判断的是"**方块是否在 5.1 格可挖距离内**"，**跟有没有工具毫无关系**。
而我们的代码把它当成"我有没有镐"：

```js
if (!bot.canDigBlock(block)) throw new NoToolError('挖 stone 需要一把镐，背包里没有');
```

石头是**埋在地下**的（正常情况都超过 5 格），于是她每次都在**还没走过去**时就被判定
"没有镐"并直接放弃——日志里她明明拿着木镐。整条链（石头 → 石制工具 → 庇护所）全断在这里。

### 一并修掉的同类问题（每一条都有实测症状）

| # | 问题 | 实测症状 | 修法 |
|---|---|---|---|
| S1 | `canDigBlock` 误用 | 拿着镐却报"没有镐"，挖矿永远失败 | 改用**背包里有没有能挖这个方块的工具**（`_hasToolFor`），距离交给走位逻辑 |
| S2 | `relocate` 每轮只往下挖 1 格，且把"换地方继续找"算作失败（3 次即放弃） | 地表到石头有 5-10 格，**永远挖不到** | 换地方=有进展；下挖深度按所处高度自适应（`(y-60)/2`，4~16 格） |
| S3 | `STONE_BLOCKS` 混进安山岩/闪长岩/花岗岩 | 挖了 18 个方块，技能判定"一个圆石都没挖到" | **两阶段**：先挖真正掉圆石的，不够才接受其它石质方块并按真实掉落计数 |
| S4 | 被埋/够不到的方块也做完整寻路 | 每挖一格白烧约 5 秒；挖 8 个圆石要 **240 秒** | 先判断"旁边有没有能站的位置"，没有就直接跳过寻路去挖开它 |
| S5 | 下挖是**竖井** | 挖到 y=54 后**爬不上来**，后续"回地表砍树"失败 | 改成**阶梯下挖**，并新增 `climbToSurface` 供后续任务脱困 |
| S6 | 短距离接近用 pathfinder | 自然地形里它原地不动、反复判"卡住" | 新增 `stepToward`/`approach`：**走不动就直接朝目标迈步** |
| S7 | 挖矿接近目标带高度约束（`GoalNear`） | 日志出现"距目标 0.4 格"却永远走不完 | 挖方块改用 `GoalNearXZ`（**只比水平距离**） |
| S8 | 完全没有脱困能力 | 卡在 1 格坑/墙角落，**连 0.4 格都走不动** | 新增 `_escapeStuck`：跳一下 → 换方向挪 → 反复几次 |
| S9 | 寻路把树叶当实心墙（`canDig=false`） | 丛林里 100 秒触发 14 次"移动卡住" | 允许**蹭掉软植被**通过，同时用 `blocksCantBreak` 把其余 896 种方块全部禁挖 |
| S10 | 选树的树冠悬空原木（离地 10+ 格） | "树好像被围起来了……够不到" | 只选**最低处原木离脚 ≤3 格**的树 |
| S11 | 木镐只有 59 耐久，挖到一半碎了 | 挖到 17 个圆石时镐碎，后续全崩 | 挖掘中每轮检查耐久，够 3 个圆石就**自动换石镐** |
| S12 | 庇护所：`ensureMaterials` 返回 `{name}` 对象却被当字符串用 | **"一块墙都没放上去"**（`countItem(对象)` 永远 0 → 第一块就 break） | 统一走 `matName()` 规范化 |
| S13 | 庇护所：`buildWalls`/`buildRoof` 内部用了未传入的 `nav` | 崩在 `nav is not defined` | 补上参数 |
| S14 | 庇护所：为差 1 块料挖 300 秒 | 有 64 块、配方要 65 块 → 卡到超时 | 用料是**估算**：达到 85% 就开工，最多补 24 块 |
| S15 | 庇护所选点把事件循环阻塞 **44 秒** | 超过 keepalive 超时 → **被踢下线** | 地面高度**缓存** + 3×3 粗查先筛 + 候选点收敛 |
| S16 | 门装不上 | `actions.lookAtPoint is not a function` | 补上这个方法 |

### 这一轮的效果（都是实测）

直接导致她**被服务器判定超时踢下线**。是日志里的"事件循环被阻塞约 44.3 秒"抓到的。
教训：**性能敏感路径上放宽范围前，先算调用次数**。

## C8. 第八轮：被困脱身 + 感知字段修复

### 1. 被困在"岩壁 + 断崖"的窄台上时完全无法移动

实测：她出生在陡峭山坡的窄台上（西北是 1-3 格台阶的岩壁，东南是断崖），
`engine_check` 的"走 15 格"报 **"移动 0.0 格"**——不是慢，是**一步都没动**。

原因：四个方向要么是石头（`blocksCantBreak` 把 896 种方块都禁挖了），要么是致命落差。
**真玩家这时会朝岩壁挖进去**，而她完全没有这个能力。

修法：
- 新增 `nav._digOut()`：朝四个方向找"挖得动又不是致命"的方块，把脚和头两层打通
- 接进 `_escapeStuck`：**跳 → 挪 → 挖墙**，三级递进
- `noPath` 且目标在 8 格内时也尝试挖开（目标就在墙后，真玩家会挖穿而不是绕整座山）；
  远处不挖，避免她在别人的建筑里乱挖
- `bot.js` 里把动作层交给导航层（`nav.attachActions(actions)`）

### 2. 给 LLM 的状态简报里，"脚下/光照/水里"永远是空的

```js
if (detail === 'brief') {
  delete snap.inventory_summary;
  ...
  return snap;              // ← 提前返回
}
const below = blockAt(bot, ...);
snap.standing_on = below ? below.name : null;   // ← brief 永远执行不到
```

`detail === 'brief'` 提前 return，而环境字段在它**之后**才计算——
也就是说**她从来不知道自己站在什么上面、是不是在水里、天黑了没有**，
而这份简报正是喂给 LLM 的那一份。已把环境字段移到提前返回之前。

### 3. "光照 0"：白天地表也报全黑

`b.light` 是**方块光**（火把/岩浆/萤石），白天地表它同样是 0。
于是简报里写着"光照 0"，她会以为天黑了该躲起来。
改成取 `max(方块光, 天空光)`。

### 4. 测试环境自身会污染世界（导致假失败）

冒烟测试自己会从脚下往下挖 3 格，洞留在出生点；历次运行把这个点挖到了基岩，
下一次运行机器人直接掉进坑底爬不出来，寻路全部失败——
**看起来像代码坏了，其实是环境脏了**。

修法：`tools/smoke.js` 支持 `MC_RCON_PORT`/`MC_RCON_DIR`，给了就
**开局复位**（从旁边未破坏的柱子取地表高度 → 补地面 → 清出站立空间 → tp 回地面）
并在挖完后**把洞填回**。复位后冒烟从 23/27 变成 **27/27**。

### 5. 火把位置

只写死两个点、且放在屋顶那一层，每次都被屋顶占住。改成
**四个内角 × 两个高度共 8 个候选**，跳过已被占用的位置。

## C9. 第九轮：操作逻辑（生存顾问 + 失败记忆）

### 问题：她会**在同一个失败上循环一小时**

她自己的记忆文件是铁证——106 条任务结果里，连续几十分钟都是同三条：
`「挖石头」连续多次没有进展` → `「做工具」挖圆石失败` → `「建庇护所」材料凑不齐` → 回到挖石头。

技能本身当时确实有 bug（见 C7），但**决策层还有第二个问题**：
LLM 只看到一段状态简报，它不知道

- **前置依赖**："我连木镐都没有，应该先砍树"——没有木头就做不了工具
- **失败记忆**："这个技能我刚试过三次都失败了"——它每次都当新任务来做
- **时序压力**："天要黑了，而我还没有能过夜的地方"

真玩家脑子里有一张清单，之前没人把这张清单交给 LLM。

### 修法：`plugin/advisor.py`（生存顾问）

把"真玩家脑子里的清单"写成规则，**输入全是真实状态**（背包/血量/饥饿/是否夜晚/背包占用/失败记录）：

| 阶段 | 判定依据 | 建议 |
|---|---|---|
| `bare` 一穷二白 | 没木头也没工具 | `chop_tree(count=4)`（**硬性**：前置条件缺失） |
| `have_wood` 有木头没工具 | 有原木、无镐斧 | `make_tools(tier=wooden)`（硬性） |
| `wooden_age` 木器时代 | 只有木镐 | `mine_stone(count=8)` → 换石镐（木镐 59 耐久 vs 石镐 131） |
| `stone_age` 石器时代 | 有石镐 | 没住处 → 攒建材/盖房；有住处 → 找铁矿 |
| `settled` 定居 | 铁器 + 有住处 | 缺食物 → 做饭；背包满 → 存东西；否则攒铁矿 |

外加三类提示：**危险**（血量 ≤6、很饿）、**时序**（天黑且没住处）、**失败记忆**（"这个技能你最近失败 3 次了，先看前置条件"）。

### 修法：失败记忆 + 防死循环闸门

- `LifeLoop.note_task_result(技能, 成功?)`：失败累加、**成功清零**（"失败过但后来做成了"不该被一直念叨）
- 决策提示词里直接列出"最近反复失败的做法"
- **闸门**：LLM 挑了一个近半小时失败 ≥3 次的技能时，**改成顾问的建议**，并把原因写进理由。
  实测日志：`她想做的「mine_stone」最近失败 3 次，改为按生存建议执行「chop_tree」（身上什么都没有，先砍点木头）`
- 建过庇护所会被记住（`has_shelter`），不再反复建议盖房

### 兜底决策也改用顾问

早期 `_fallback_decision` 是写死的"驱动 → 技能"映射，有两个毛病：
用了 `move.to` 这种底层命令（`skill.run` 根本不认），而且完全不看状态——

### 3. 光照语义：一个两头都会错的坑

b.light      // 方块光源（火把/岩浆/萤石）——白天地表也是 0

## C11. 第十一轮：像人一样移动

### 破绽一：瞬间转头（最容易被一眼看穿）

```js
// mineflayer 的实现（lib/plugins/physics.js）
bot.look = async (yaw, pitch, force) => {
  const yawChange = Math.round((yaw - bot.entity.yaw) / sensitivity) * sensitivity
  bot.entity.yaw += yawChange        // ← 一次就把整个角度转完
  if (force) { ...; return }         // ← force 只影响"是否等服务器确认"
  await lookingTask.promise
}
```

**`force` 的真假不改变旋转方式**——两种情况都是一步到位。也就是说"渐进转头"必须自己插值。
而我们代码里原本有 **6 处** `bot.look(..., true)` / `bot.lookAt(..., true)`。

新增 `bot/humanize.js`：

| 能力 | 做法 |
|---|---|
| `smoothLook` | 把一次旋转拆成 2~10 小步，每步发一次视角包；时长按角度自适应（70~320ms），曲线"起手快、收尾慢" |
| `smoothLookAt` | 看向某个坐标（含 `eyeOffset`，像人在看"人"而不是看脚） |
| `WalkGaze` | 走路时叠加 ±8° 的缓慢扫视（正弦），真人不会死死盯着正前方 |
| `Gait` | 步态：近了不冲、远了才冲，还有"悠闲/正常"两种心情（20~60 秒切换） |
| `maybeIdlePause` / `idlePauseMs` | 偶尔停 0.26~0.78 秒，像在确认方向 |
| `idleLookAround` | 空闲时东张西望（±40° 内） |

**接入点**：`nav.look` / `nav.lookAtPoint`、`stepToward`、`common.js` 的 `walkDirect`、
`actions.dig`（挖掘前看向方块）、`actions.place`、`actions.attack`（瞄人），
以及 `_keepAliveTick` 里的**空闲环顾**（只在无任务、无窗口时触发，不会干扰窗口事务）。

**终点角度与瞬间对准完全一致**，所以服务器对朝向的判定（挖掘/放置要求看向目标）不受影响。

### 破绽二：永远在冲刺

原来 `sprint = dist > 2.5` 是恒定判断。现在由 `Gait` 决定：近距离从不冲刺、
远距离按心情随机（悠闲时 25%，正常时 50~85%）。

### 破绽三：走得像尺子量过

走路时会左右轻微扫视、偶尔停半秒、停下时顺手看一眼旁边。

角度环绕取最短路径（3.0 → -3.0 只差 0.28 弧度）、扫视幅度 ≤0.15 弧度（不会把身体带偏）。

## C12. 第十二轮：把决策权还给 LLM，并让"过日子"有连续性

用户的验收标准说得很清楚：**像真人一样地生存，同时 LLM 还能决定要干什么**。
对照这条标准，之前的设计有两个真问题（其中一个是我自己上一轮引入的）。

### 问题一：过日子的 LLM **没有工具，不能自己查看**

```python
# main.py 里的 _llm
resp = await self.context.llm_generate(chat_provider_id=..., prompt=..., system_prompt=...)
```

`llm_generate` **不带任何工具**。也就是说她"决定要干什么"的时候只能看一小段固定简报，
**不能主动去看**：背包里到底有什么、附近有没有树、天还有多久黑、旁边有没有怪。

真人是先看一圈再决定的。结果是她的决定经常和现实脱节
（身上没木头却决定去做工具），然后失败、再决定、再失败。

**修法**：新增 `plugin/perception_agent.py`——给决策阶段一套**只读**感知工具，
让 LLM 先查再决定：

```
LLM（带 mc_status / mc_inventory / mc_scan / mc_players / mc_skills / mc_her_memories）
  → 决定查看什么 → 执行 → 结果喂回 → …… → 输出最终决定 JSON
```

- 只给**只读**工具：动作类（mc_goto / mc_chop_tree…）是"决定之后"才该用的，属于执行层。
  决策阶段能随手调它们会变成"还没决定就先动手"，而且决策本不该有副作用。
- 拿不到工具（没 provider / 工具管理器不可用）会自动退回纯文本决策，功能不受影响。
- 日志里能看到她查了什么：`她决定前先查看了：mc_inventory、mc_scan`

### 问题二：每 90 秒从零决定一次，**没有连续的打算**

真人心里一直有件事在推进（"我要盖个能过夜的地方"），而不是每 90 秒掷一次骰子。
之前每次决策都是独立的，所以她看起来"想一出是一出"，生存进度也很慢。

**修法**：`LifeDecision` 增加 `intention` 字段，**由 LLM 自己设定**：

- 提示词里带上"你正在做的事（打算）：X（已经做了 N 轮）"
- 模型可以在 JSON 里写新的打算、保持不变、或填 null 放下它
- 存进 `life.json`，**重启插件后她仍然记得自己要做什么**
- 细节：模型**漏了** `intention` 字段时保持原打算不变（防误伤）；
  只有明确写 null/空串才放下

### 问题三（我上一轮的错）：规则**抢了 LLM 的决定权**

上一轮我加的"失败 3 次就改成顾问建议"是这样的：

```python
if fails.get(skill, 0) >= 3:
    return LifeDecision(skill=advice.skill, ...)   # ← 直接替它决定了
```

这违背了"LLM 决定要干什么"。**改成"把失败记录摆到它面前，再问一次"**：

1. 她选了最近失败 ≥3 次的技能 → 第二次提示里明确点出"这个做法已经失败 N 次了，
   请重新考虑：换做法、先解决前置条件，还是坚持（坚持就说明这次有什么不同）"
2. 她改主意 → 采纳她的新选择
3. **她坚持 → 尊重她的决定**（她可能认为上次失败是地形问题，这次换了地方就能成）
4. 只有在失败 ≥5 次**且**她仍然坚持时，才退回规则兜底——纯粹为了避免实测过的
   "一小时死循环"。日志会写明：`「mine_stone」已连续失败 5 次且她仍坚持，退回生存兜底`

顾问（`advisor.py`）的定位也随之明确：**它只是参考信息**，提示词里明确写着
"决定权在你：「生存现状」那段只是参考，你可以按自己的想法来"。

### 验证：`test_advisor.py` 扩到 **40 项断言**

新增的关键断言：

| 断言 | 说明 |
|---|---|
| 会把"失败过 3 次"明确告诉她 | 第二次提示里点明 |
| 她改主意后尊重新选择 | **不是被规则改掉** |
| 她坚持时尊重她的决定 | 3 次还不到兜底线 |
| 失败 5 次仍坚持时退回兜底 | 避免死循环 |
| LLM 设定的打算被记住 / 轮数累加 | intention 生效 |
| 模型漏字段时不清空打算 | 防误伤 |
| 端到端：失败后再问一次 → 改主意被采纳 → 打算被记住 | 全链路 |

## C13. 第十三轮：短期记忆与死亡后的反应

这一轮继续沿着"像真人一样生存 + LLM 决定"往下补两件真人一定会做、而她之前做不到的事。

### 1. 决策时**看不到"刚才发生了什么"**

之前的决策提示词里只有【当前状态】（此刻的位置/血量/背包）和【生存现状】，
**没有任何"我刚才在干嘛、成没成"**。真人做决定时会回想这些——
"我刚才砍树没找到树，那换个方向""我刚挖到石头了，接着做工具"。

结果就是她的决定看起来像失忆：明明上一轮刚失败，这一轮又从头开始想。

**修法**：新增"最近做过的事"短期记忆（保留最近 8 条，渲染最近 5 条）：

```
【你的近期经历】
- 你最近做过的事：
    21:43  chop_tree → 做成了
    21:43  mine_stone → 没做成：连续多次没有进展
    21:43  chop_tree → 没做成：附近找不到树
```

### 2. 死亡后**不知道自己的东西掉在哪**

引擎侧本来就有 `bot.death` 处理（通知 + 写记忆 + 用她的语气说一句），
**但决策层完全不知道这件事**。而 MC 里掉落物**大约 5 分钟就消失**——
不知道就等于永远不会回去捡。真人死了第一反应是"我的东西！"

**修法**：`LifeLoop.note_death(position)`，并在提示词里明确写出来：

```
- 你 0 分钟前在 (100, 12, 200) 死了，**身上的东西都掉在那里**
  （MC 里掉落物大约 5 分钟就会消失）。要不要回去捡，你自己决定。
```

注意最后一句：**要不要去捡由 LLM 决定**，不是规则命令她去。
超过 6 分钟就不再念叨（东西早没了）。

### 3. 卡住的打算会被点出来

如果同一件事做了 ≥4 轮还没成，提示词里会加上：

```
——注意：这件事已经做了 5 轮（约 10 分钟），最近失败了 3 次。
真人这时会停下来想想：是卡在某个前置条件上（缺工具？缺材料？地形不对？），
还是该先做别的事、或者换个做法。**你也可以干脆放弃这个打算。**
```

这是"像人一样"的关键一步：真人不会无限重复，也不会被规则硬掰——**它自己决定放不放弃**。

### 验证（`test_advisor.py` 扩到 **50 项断言**）

新增：记下失败原因 / 也记下成功 / 死亡地点会告诉她 / 提醒掉落物 5 分钟时限 /
把决定权留给她 / 太久远的死亡不再提醒 / 最近经历只保留 8 条 /
卡住的打算会点出轮数与失败次数并提示可以放弃。

## C14. 第十四轮：真实环境暴露的"她完全不动"

这一轮**全部问题都来自在用户真实服务器上的实测**，而不是我的测试服。

### 症状

用户说"她还是不能自己活动"。日志给出的证据是**她在同一个困境里挣扎了一小时**：

```
22:43 <AstrBot> 路被挡死了……走不过去，镐子没做成
22:50 <AstrBot> 路被方块挡死了，走不过去，木镐没做成
23:03 <AstrBot> 路被堵死了走不过去……所以木镐还没做成
23:10 <AstrBot> 路被堵死了走不过去，石镐没做成
23:15 <AstrBot> 差十格……路被堵死了走不过去，木镐没做成
23:20 <AstrBot> 黑漆漆的……前面的路根本过不去嘛
```

### 用 RCON 查她的真实处境（这是关键一步）

```
位置: (123.7, 58.0, -252.3)    ← 地下（地表在 y≈66）
背包: （空）
```

再用 `/execute if block` 逐格探测她周围的方块，得到剖面：

```
y=58（她的脚）:  ####..###     ← 只有 2 格宽的横向通道
y=59（她的头）:  #########     ← 头顶被封死！
```

**她挖矿时把自己封在洞里了**——脚那层是通道，头顶那层全是实心。
于是任何寻路都失败，所有需要走动的技能（做工具要走到工作台、砍树要走到树）全部失败。

### 三个真 bug

| # | 问题 | 后果 | 修法 |
|---|---|---|---|
| 1 | 脱困逻辑只看四个水平方向，**没想过要挖头顶** | 被自己封住时永远出不来 | 反射层新增 `_blockingSelf()` + `autoUnstuck`：检测"所在格/头顶是实心"就立刻挖开，**优先级等同致命级** |
| 2 | 脱困时**不挑挖得动的方块** | 她背包空、石头徒手挖不动 → 自救任务每 8 秒失败一次、无限重试 | 按"徒手可挖"排序（泥土/沙/树叶优先），水平方向也一起找；彻底挖不动时**在游戏里求助**并把情况写进状态简报 |
| 3 | 感知工具**字段名是我凭空造的** | `ToolCallMessageSegment` 只有 `role/content/tool_calls/tool_call_id`，我却传了 `tool_name`/`tool_args` → 每次抛 `validation error` → **"先查看再决定"整条路径每次都失败** | 照抄能正常工作的 `game_agent`：`AssistantMessageSegment(tool_calls=resp.to_openai_tool_calls_model())` + `ToolCallMessageSegment(tool_call_id=..., content=...)` |

### 还有一个"看起来完全不动"的原因

```
[23:31:45] 想事情超时（90 秒），本轮跳过；下一轮再想
```

决策超时 90 秒 + 决策间隔 90 秒 = **她有 3 分钟完全不动**。
而且感知路径每次抛异常要白等一次 LLM 往返，更容易撑到超时。

修法：

- 感知决策连续失败 3 次 → **熔断 10 分钟**退回纯文本（保证她至少还在动）

## C15. 第十五轮：把"她不动"从**节奏**上根除

### 症状：她看起来"做完一件事就呆住了"

实测她的**决策间隔是 190~200 秒**，而配置里写的是 90 秒。原因在循环里：

```python
await asyncio.sleep(90)                  # 固定等 90 秒
...
self._busy_until = time.time() + 120     # 做完一件事再压 120 秒
```

**90 + 120 = 210 秒**。哪怕技能 10 秒就做完了，她也要干站着三分半才想下一件事。
真人做完一件事会**立刻**想下一步——这就是"她不动"的观感来源。

### 修法一：可被唤醒的等待

```python
try:
    await asyncio.wait_for(self._wake.wait(), timeout=self._decide_interval)
    self._wake.clear()
except asyncio.TimeoutError:
    pass
```

任务结束时（`task.finished` / `task.cancelled`）插件调用 `life.wake()`，
她**立刻**继续想下一步。动作后的等待从 120 秒压到 **8 秒**
（真正该用的信号是"引擎里还有没有任务在跑"，那是 `_engine_busy` 的职责）。

### 修法二：超时之后要尽快重试

```
[23:31:45] 想事情超时（90 秒），本轮跳过；下一轮再想
```

决策超时 90 秒 + 间隔 90 秒 = **3 分钟完全不动**。而且决策现在可能包含多次
LLM 往返（查看 → 决定 → 失败后重问），90 秒太容易踩到。改为：
- 超时 90 → **150 秒**
- 超时后**只等 8 秒就重试**（不再等满一个完整间隔）
- 感知决策连续失败 3 次 → **熔断 10 分钟**退回纯文本（保证她至少还在动）

### 修法三：修掉自己引入的误伤

新加的 `autoUnstuck` 反射一开始是 **critical 级**（会抢占并取消正在跑的技能），
而"被卡住"的判定在边界情况下会误报（她站在方块边界、被传送进某格、正在挖自己站的那格）。
**实测后果**：`mine_ores` 在 9.9 秒被莫名取消，`engine_check` 5/6、`crafttest` 7/8 跟着挂。

最终的判定设计（三级防护，不靠门槛）：

| 防护 | 作用 |
|---|---|
| 反射用 `normal` 级（**不抢占**） | 误报只会让一个挖方块的小任务排队，**绝不会取消她正在跑的技能** |
| 取整前加偏移量（`floor(y+0.1)` / `floor(y+1.62)`） | 消除"站在方块边界时把脚下地面误判成卡住" |
| 连续两次确认（相隔 2 秒） | 滤掉瞬时抖动 |

**刻意不要求"她静止不动"**：实测完全被埋住时服务器会推动她、位置一直微动，
"静止 N 秒"这个门槛永远满足不了、她永远出不来。

### 验证：新增 `bot/tools/test_life_rhythm.py`（4 项断言）

| 断言 | 结果 |
|---|---|
| 循环能自己跑起来并做出决定 | ✅ |
| **唤醒后 4 秒内就继续想**（不必等满间隔） | ✅ |
| 忙的时候不会插进来（不打断正在跑的技能） | ✅ |
| `wake()` 会清掉 busy 标记 | ✅ |

### 又一个我自己的教训

这一轮我**三次**把测试写错、并因此误判代码有问题：

## C16. 第十六轮：用户实测的四条反馈

用户原话（每条都对应一个具体缺陷）：

> "现在的机器人还是不能很好的完成我的指令，比如我让她做把木镐就失败了，
> 而且现在似乎没有接到我的指令还是不会主动行动，动作也很生硬，跟着我的时候是一顿一顿地动"

### 反馈 1：跟着我一顿一顿 —— 已修

根因：跟随用的是**每 600ms 重设一次 `pathfinder.setGoal(GoalFollow, true)`**，
每次重设都让 pathfinder 停下、重算路径、再起步 → 走两步停一下。

改成**真人跟人的方式：持续朝目标走**（每 120ms 修正朝向，方向键一直按着）：

| 机制 | 说明 |
|---|---|
| 主模式 | 直接朝目标走，不寻路（连续运动） |
| 距离控制 | 迟滞但**无死区**：走着→到 `stopAt` 才停；停着→超过 `startAt` 就走（早期有死区，她 6 秒一步没挪） |
| 一直看着对方 | 平滑看向目标**头部**（不是脚） |
| 被挡住 | 才临时交给 pathfinder 绕一小段，绕过去继续直接走 |

**验证**（新增 `test_follow_smooth.js`，逐帧采样位置量化）：

| 指标 | 修前 | 修后 |
|---|---|---|
| 采样帧中"在动"的比例 | **0/87 帧** | **70~78/85 帧** |
| 单帧位移中位 | 0.000 格 | **0.220 格**（连续行走） |
| 目标走远后 | 不跟 | 跟到 1.5~2.2 格 |
| 贴近后 / 叫停后 | —— | 站住 0 抖动 / 真的停住 |

### 反馈 2：让她做木镐失败 —— 三处根因

日志里的真实调用链：

```

mc_craft(spruce_planks)  → （她手上是云杉，模型挑错了木头）
mc_craft(wooden_pickaxe) → 又失败
mc_inventory → mc_collect → mc_task_status
→ "游戏内对话的工具循环超过 6 步，中止"
```

| # | 根因 | 修法 |
|---|---|---|
| 1 | **工具循环上限 6 步**，一条完整合成链根本不够 | 6 → **12 步** |
| 2 | 选配方时**只看"是否需要工作台"，完全不看她有什么木头** | 按"**材料能不能从手上推出来**"排序（有 spruce_log ⇒ spruce_planks 可做） |
| 3 | 报错只说"还差 oak_planks×3" | 报错**具体化**：`你手上有 spruce_log，可以先 mc_craft(spruce_planks)` |

**顺带修掉一个更深的坑**：合成后**服务端背包同步是异步的**——

```
craft(spruce_planks×4) → 返回 ok:true、delta {spruce_planks:4}
紧接着读背包 → {"spruce_log":3}          ← 木板还没到
下一轮再读 → {"spruce_log":3,"spruce_planks":4}
```

后果：① 链式合成每一步都看不到上一步的产物 → **链条必断**；
② 误判"没有产出"→ 重试 → **超产**（实测要 4 个木板做出 12 个）。
修法：`craftOnceAndSettle` —— 每次合成后**等产出真正落到本地背包**再判断。

**修后实测**：`craft planks` → `craft stick` 连续成功，
`bot.inventory.items()` / 原始 `slots` / `inventory.get` 三处读数**完全一致**；
`craft wooden_pickaxe` 报的是**正确原因**——「需要工作台才能合成」并告诉她先做工作台。

### 反馈 3：不主动行动 —— 其实是被"跟随任务"占住了

17:21 用户让她"跟着我"→ `mc_follow` 任务一直在跑；

## C17. 第十七轮：任务排序（连续行动）+ 视线检查 + 怪物规避

用户的三条新反馈：

> "现在的问题是不够连贯，我希望做一个任务排序的功能，让她能连续行动，
> 每一次进游戏也会生成一个任务。然后，现在她挖东西会隔着墙挖，不会躲避/攻击敌对生物"

### 1. 任务排序：让她连续行动 —— 新增"计划队列"

**问题**：早期每做一件事都要重新问一次 LLM（一次往返十几秒到几十秒），
于是她做完一步就呆站着想下一步，一点都不连贯。

**修法**：让 LLM **一次给出有序的几步**（`plan`），循环里按顺序执行，
**中间不再问模型**：

```
LLM 一次输出：
  plan = [砍树 → 做工具 → 挖石头]

循环里：取队首执行 → 引擎空闲 → 再取队首执行 → …… 全部做完才重新问 LLM
```

| 机制 | 说明 |
|---|---|
| `plan` 字段 | LLM 输出 2~5 步的有序安排（每步含 skill/params/why） |
| 队列 | `LifeLoop._plan`，先进先出 |
| 队首立刻执行 | 本次决定 = 计划第一步，剩下的进队列 |
| **一步失败就丢弃剩余计划** | 计划是按"前一步成功"排的，失败还硬做后面只会连环失败；丢掉后重新问 LLM |
| **每次进游戏清空重排** | 用户要的"每一次进游戏也会生成一个任务"就落在这里（`bot.spawn` → `life.on_session_start()`） |
| 兼容旧格式 | 只给 `skill`+`params` 时自动包成一步的计划 |

**验证**（`test_life_rhythm.py` 扩到 **12 项断言**）：
计划的第一步成为当前决定 ✓、剩余步骤进队列且顺序保持 ✓、出队顺序正确 ✓、
一步失败丢弃剩余计划 ✓、进游戏清空重排 ✓、无 plan 字段兼容 ✓。

另有一次端到端追踪证明真的连续执行：
```
parse->skill=chop_tree pending=['make_tools', 'mine_stone']
SUBMITTED: ['chop_tree', 'make_tools']      ← 连续两步，中间没问 LLM
```

### 2. 隔着墙挖 —— 加视线检查

**根因**：`findNearestDiggable` 只按**距离**选目标，完全不看她看不看得见。
于是她会对着墙猛敲、方块其实在墙后面。

**修法**：取一批候选（16 个），顺次找"**最近且看得见**"的那个：

```js
candidates = bot.findBlocks({ matching, maxDistance: radius, count: 16 });
for (const pos of candidates) {
  if (!canSeeBlock(bot, block)) continue;   // 看不见就跳过
  return block;
}
```

`canSeeBlock` 优先用 mineflayer 的 `bot.canSeeBlock`（真正的射线检测），
拿不到就退化成"六个面里至少有一个是空气"（说明至少露了一面）。

**回归确认没有误伤**：minetest（挖矿→熔炼→铁镐）**13/13** 仍然全过。

### 3. 不会躲避/攻击敌对生物 —— 两处修

| 症状 | 根因 | 修法 |

| **不躲避** | pathfinder 默认不认识怪物，`entitiesToAvoid` 是空集合 → 她会直直地从僵尸/苦力怕身边走过 | 把 34 种敌对生物加进 `movements.entitiesToAvoid`，寻路就会把它们当障碍绕开 |
| **不攻击** | 反击半径只有 4 格（怪贴脸才还手，往往已经挨了两下）；而且普通反射**只排队**——她正在挖矿时"排队等挖完再还手"等于站着挨打 | 半径 4 → **6 格**；贴身（≤3 格）时用 **critical** 抢占当前任务（真人这时会立刻放下手上的活），远一点用 normal 不打断她 |

## C20. 第二十轮：知识库 + 可观测性 + 工作站记忆

用户要求"全部方向都做，另外做一个类似知识库的东西，让她会学着怎样做更好"。

### 一、知识库（`plugin/knowledge.py`）—— 会自己长大的经验

三层知识，来源与作者各不相同：

| 层 | 来源 | 存哪 | 谁写 |
|---|---|---|---|
| **攻略** | 人写的 6 篇 Markdown | 仓库（只读） | 我 / 用户 |
| **教训** | 她从失败里提炼的 | `data/knowledge/lessons.json` | **她自己** |
| **笔记** | 坐标与发现 | `data/knowledge/notes.md` | **她自己** |

**学习回路**（这是"会学着怎样做更好"的落地点）：

```
同一技能连摔 3 次 → 把「报错 + 当时处境」交给模型 → 让它写一条可复用的经验
→ 存进教训库（带标签、去重）→ 下次遇到同类事情按标签检索出来喂回提示词
```

**为什么是"第 3 次"**：第一次可能是偶发、第二次可能是运气，连续三次才是规律；
而且每次失败都调模型总结太贵（一次往返几秒 + token）。

**四个关键设计**（都有测试钉住）：

| 设计 | 说明 | 实测 |
|---|---|---|
| **去重** | 同一个坑不该记十条 | `"挖石头前先确认手上有镐"` ↔ `"挖石头前一定要先看看有没有镐"` 相似度 **0.38** → 判重 ✓（阈值 0.35 是实测分界：不同主题 0.00 / 同义 0.71） |
| **过滤废话** | 模型很容易写"我失败了，下次小心" | 这类一律不入库 ✓ |
| **有上限** | 否则无限膨胀、污染提示词 | 最多 120 条，超了淘汰"最久没用过"的 ✓ |
| **标题如实** | 没经验时不该冒充经验 | 只指向攻略时用"可能有用的攻略" ✓ |

相似度用 **Jaccard 与包含度的较大值**：中文短句的共同关键词占比小，
纯 Jaccard 会把同一个坑判成不相似（实测 0.21），包含度能抓住"一句基本被另一句覆盖"。

新增 3 个工具（共 **52 个**）：`mc_knowledge_search` / `mc_knowledge_add` / `mc_knowledge_note`

### 二、可观测面板（5.4）—— "她为什么不动"一眼可见

前几轮排查"她卡住了/不动"时，每次都要写临时脚本、翻几百行日志、逐条猜。
numen 的做法是把"她忙不忙、为什么不动、排着什么"集中在 `LoopStatus` 一处读——照做：

- 引擎新增 `diagnose()` + `status.diagnose` RPC
- 把"可能导致她不动"的原因**全部列出来并标明当前哪条成立**：
  没连接 / 引擎最近被阻塞过 / 有任务卡着超过 90 秒 / 反射在退避 / 血量饱食危险 / 正在下坠
- 插件新增 `/mc诊断`（别名 `诊断`、`mc她怎么了`、`mcdiag`），输出：
  结论 → 位置血量 → 手上在做什么 → 排着几个 → 最近一次引擎阻塞 → 本能活动时间 → 最近失败
- `LifeLoop.failure_summary()`：她最近在什么事上反复摔跟头

顺带把"最近一次事件循环阻塞"存成结构化数据（原来只打日志），诊断里能直接读。

## C21. 第二十一轮：蓝图精细建造（2.1）

用户最初就想要"建一个房间"，而原来的 `build_shelter` 只会盖"四堵墙 + 一个顶"的方盒子——
没有窗、没有屋檐、没有隔断，门和火把的位置也写死。numen 的做法是 `Blueprint`：
**给一张图纸就照着搭**。这里照做，但**图纸由 LLM 自己画**（它本来就是最会设计的那个）。

### 图纸格式（刻意做成模型容易写的形状）

```json
{
  "name": "石基小屋", "size": [5, 4, 5],
  "palette": { "S": "cobblestone", "P": "oak_planks", "G": "glass",
               "D": "oak_door", "T": "torch", ".": null },
  "layers": [
    ["SSSSS", "SSSSS", "SSSSS", "SSSSS", "SSSSS"],
    ["SPGPS", "P...P", "P.D.P", "P...P", "SPGPS"],
    ["SPGPS", "P...P", "P...P", "P...P", "SPGPS"],
    ["PPPPP", "PPPPP", "PPTTP", "PPPPP", "PPPPP"]
  ]
}
```

`layers[0]` 是最底下一层；每个字符串是一行（z），每个字符是一格（x）。
写起来像画画、读起来直观、**而且可以校验**。

### 三个真问题（都是实测撞出来的）

| # | 问题 | 后果 | 修法 |
|---|---|---|---|
| 1 | 我第一版图纸的**中间层只放了四角** | 上一层的墙/门/窗**下面是空的** → 报"周围没有可以依附的方块"，**21 块墙没搭上去** | 重画三张内置图纸，每层都完整；并写进测试：**每个方块至少要有一个相邻实体方块** |
| 2 | 放置顺序按"离原点近" | 屋顶中间正下方是屋里（空气），先放中间就没东西可依附 | 改成**自下而上 + 同一层从边缘往里**（离本层中心由远到近）→ 永远有已放好的邻居 |
| 3 | `mc_blueprint` 工具里有 `yield`（错误分支），末尾却写 `return await ...` | **`SyntaxError: 'return' with value in async generator`** → 插件整个加载失败 | 改成 `yield await ...`；并**扩展 `check_await.py`** 静态拦住这类错误 |

第 3 条尤其值得记：那个错误**语法检查通过、大部分测试也过**，只有真正 import 才炸。
静态检查是唯一能在写的时候就拦住它的手段。

### 二、5.2 真实环境回归：**在用户自己的服务器上跑**

新增 `bot/tools/regress_real.js`——连用户的服务器（25565），**只读不写**
（只连接、观察、走路、量阻塞，不挖不放，用户名带 `Regress` 前缀，跑完立刻断开）。

**为什么必须做**：前面所有测试都在我的超平坦测试世界里跑（地面平整、没有树、
没有峡谷）。而真实地形反复咬我——"隔着墙挖""被自己封在洞里"都只在那里出现。

#### 第一次跑就抓到一个真 bug

```
进服位置 (7, 74, -9)，脚下 spruce_log   ← 她生成在树冠里！
move.to 走 20 格 → 实际只移动 1.1 格，20 秒
路线计划：直线方向上有 8 段被挡：要挖 spruce_leaves×1…
```

**根因是我上一轮的改动**：我为了治"乱挖"把 `canDig` 整个关掉，
结果**出生点在树冠里时她被树叶困死**（走路不挖世界 = 被树叶挡住）。

**修法**：恢复"软植被可以蹭掉"，但**保留其它防乱挖的修复**——因为真正造成
"乱挖"的两个原因已经单独修掉了，跟这里无关：

1. `_blockingSelf` 会返回她根本挖不动的方块 → 反射层反复重试（已修：只挖挖得动的）
2. `_climbTowardLevel` 在任何寻路失败时都会挖（已删：那是我自己加的兜底）

而且寻路**只在路径确实需要时才挖那一格**；其它 896 种方块仍在 `blocksCantBreak` 里
（墙、地板、别人的房子都不动）。想要完全不动世界可以设 `MC_ALLOW_SOFT_DIG=0`。

## C23. 第二十三轮：MLG 落地水（3.1）—— 找到四个真原因，但**仍未完成**

这一轮把 MLG 从头查了一遍，**每个环节都有实测证据**，但结论是：
**它现在还是救不了命**。如实记录，免得下一个人（或下一轮的我）重复踩。

### 查出来的四个真原因

| # | 原因 | 证据 | 状态 |
|---|---|---|---|
| 1 | **`entity.velocity` 完全不可信** | 诊断视图里的 `mlg_last_air_vy`：她从 18 格坠落时速度只有 **-0.078**，而阈值是 -0.7 → MLG **一次都没触发** | ✅ 改成**位置变化率**（实测 12~36 格/秒，判断准确） |
| 2 | **动作窗口太窄** | 实测坠落速度 23 格/秒，3~5 格窗口只有约 90ms，而检查间隔 100ms → 只有一次机会 | ✅ 窗口放宽到 7 格 + 坠落时额外插两次 33ms 的检查 |
| 3 | **`place(reach:true)` 会尝试寻路（15 秒超时）** | 人正在坠落，第一次尝试就卡 15 秒，`_mlgRunning` 一直为 true，后续全被挡掉 | ✅ 改成 `reach:false` + 400ms 硬超时 |
| 4 | **`_currentReflexRunning` 门控把它挡在门外** | MLG 是最高优先级本能，却被"反射层正在跑"挡住 | ✅ 去掉这个门控（只保留"上次自救没做完"） |

### 但仍然失败，原因也查清了

**倒水这条路服务端不接受**：装备了桶（`held: water_bucket` 确认过）、
`activateBlock` / `activateItem` 两种包都试过，**世界里一滴水都没出现**，
桶也没变成空桶。这是 mineflayer 在这个场景的固有局限。

**垫方块这条路需要"旁边有墙"**：我造的测试场地是 **7×7 的空井**——
脚下那格是空气、**周围也是空气**，没有可依附的方块 → 放置被拒。
真人挖的是 1 格宽的竖井，那种情况才有墙可贴。

最后一次在 1 格宽竖井里的测试：从 24 格掉下来**血量 20/20（没摔伤）**，
但井里**没有找到她垫的方块**——所以"是 MLG 救的"**没有得到确认**。

### 诚实结论

**MLG 目前是"能发现危险，但救不了自己"**。已经修好的部分（速度判断、动作窗口、
不寻路、优先级）都是有价值的，但**核心动作（倒水/垫方块）在服务端不被接受**。
下一步要做的不是调参，而是换机制——比如：
- 用 `bot._client.write('block_place', ...)` 自己构造包（绕过 mineflayer 的封装）
- 或者干脆放弃"落地水"，改成**提前预防**（走到悬崖边时先垫一格、下矿只挖阶梯）

### 顺带修好的一个通用问题

`useBlock` 原来**不装备物品**就右键方块。实测倒水桶时"成功"了但没倒出水，
因为手上拿的是别的东西。现在支持 `item` 参数，会先装备再点。

## F. 本轮修复的真实缺陷（都是实测暴露的）

记录在这里是为了说明"为什么这些测试值得存在"——它们每一个都曾让功能**看起来能用其实不能用**。

| 缺陷 | 症状 | 根因 |
|---|---|---|
| `blockAt` 无限递归 | 脚下永远是"未知方块"，寻路找不到路 | 批量替换脚本把 helper 的函数体也替换成自调用；被 `catch` 静默吞掉 |
| 传普通对象给 mineflayer | `pos.floored is not a function` | mineflayer 需要真正的 `Vec3`，普通 `{x,y,z}` 会崩 |
| `goal_updated` 当成功 | **寻路 1 秒就报"完成"，实际没动** | `setGoal` 后框架立刻触发一次 `goal_updated`，被误判为到达 |
| 树冠里寻路必失败 | 出生在丛林树上时"找不到路径" | pathfinder 的 `maxDropDown=3`，不会从 30 格高的树冠往下走 |
| `findLogBlock` 步长 2 | **附近有树却一直报找不到** | 步长扫描漏掉奇数坐标的树干 |
| 掉落物够不到 | 砍树进度永远停在 `0/N` | 站在树冠上挖，掉落物落到下方树叶上，原地够不到 |
| 掉落物按方块名统计 | 明明捡到了却报"没捡到" | 挖草方块掉的是泥土，名字不一致，必须用背包差分 |
| `waitForChunksToLoad` 拖慢进服 | 每次进服白等 10–15 秒 | 该 API 要求 5×5 区块全就绪；改为只等脚下那一列 |
| 错误码被压平 | 插件无法区分"没进服"与"动作失败" | `wrap()` 把所有错误转成 GAME_ERROR |
| 批量替换的副作用 | `actions.blockAt(bot, ...)` 这种不存在的调用 | 正则替换误伤 `actions.bot.blockAt` |
| 合成依赖死锁 | 做工作台要木板，做木板却说"需要工作台" | 用配方 `ingredients` 的行列数猜是否需要工作台，而 `jungle_planks` 的配方形状是 1 行 3 列，被误判；改为"先试随身合成，报错再放工作台"的自适应策略 |
| 反射层抢占用户任务 | "让它砍树，它中途去吃了口饭，砍树任务就没了" | 普通反射（饿/低血）与用户任务同处一个优先级队列且更优先；改为分级——只有溺水/岩浆/着火能抢占，其余排队等待 |
| 残血时刷屏重试 | 日志里连续 6 条一模一样的"血量过低，后撤：移动卡住" | 撤退反射无条件触发且无冷却；改为"确实有威胁 + 20 秒冷却" |
| 技能"假成功" | `mine_stone` / `make_tools` 什么都没产出却返回 `done` | 用内部循环是否跑完当成功判据；改为以**背包里真的多了东西**为准 |
| 装备悄悄失效导致放置失败 | 放工作台报 mineflayer 的 `must be holding an item to place` | `bot.equip(item,'hand')` 用的是旧物品对象（槽位已变），静默失败；新增 `holdItem()`：重新按名字取物品 → 装备 → **验证 heldItem** → 重试 |
| 测试脚本自己引入失真 | 为清空背包把机器人切创造模式后，"挖了方块却没有掉落" | 创造模式挖掘瞬间破坏且无掉落；改为让机器人用 `bot.toss` 自己丢光物品，并在准备阶段断言 `gamemode === 'survival'` |
| **放置方块静默失败** | 物品被消耗了，方块却没出现在世界里 | 用的是底层 `bot._genericPlace()`——它只发包、不等服务器回执，被拒绝时也"成功返回"。改用公开的 `bot.placeBlock()`，它会等 `blockUpdate` 并在被拒时抛错 |
| **长任务后必然掉线** | 挖矿→熔炼→做工具，走到第三步连接被重置（`ECONNRESET` / 服务端 `lost connection: Timed out`） | minecraft-protocol 的 keep-alive 是**被动**的：只在收到服务端 `keep_alive` 后计时，服务端忙于生成区块时发不出包，本地回环上也会因此超时。修法两条：① 引擎每 10 秒主动发一次视角包（真玩家也一直在发包）；② 超时容忍 30s → 180s。修后连续 4.5 分钟不掉线（此前 2 分钟内必断） |
| **测试脚本拉到子进程就 EPERM** | 测试里"rcon 失败：spawnSync … EPERM"，表现像 rcon 坏了 | 受限环境下"捕获子进程输出"（stdio pipe）会被拒。改为**进程内** RCON 客户端（`tools/lib/rcon.js`），彻底去掉子进程 |
| **RCON 响应被丢弃** | `forceload`/`fill` 返回空字符串，场景造不出来 | 两个实现错误：① 不能按 `type===3` 判断认证响应（Paper 返回 id=1/type=2）；② 认证后立刻把 pending 置空，而命令响应可能在同一个 I/O 块里重入到达，被当成无主响应丢弃。改为保留 pending + 累积到 `type===0` 的结束包 |
| **超平坦世界生成异常** | 机器人站在基岩上、地形时有时无、寻路原地失败 | 手写 `generator-settings` 的 JSON 在 1.20.1 上不可靠（会生成"基岩层与空气层混杂"的坏地形）。改用 `level-type=flat` 的默认经典超平坦，不写 `generator-settings` |
| **测试环境脏导致误判回归** | 跑几轮后冒烟从 26/26 掉到 22/26，看着像代码退化 | 测试会真的挖穿世界，机器人掉进自己挖的洞里。新增 `tools/reset_world.js`，并在文档里写明"跑测试前先重置世界" |
| **配方需求算错（假"材料不足"）** | 有 6 个木板 + 4 根木棍却说"材料不足"，工具永远做不出来 | 有序配方的 `recipe.ingredients` 是**空数组**（mineflayer 只在无序配方上填它）。正确数据源是 `recipe.delta` 里 count 为负的项 |
| **`bot.craft` 的 count 参数不可靠** | `count:2` 只产出 1 份；`stick` 更是让 Promise 永不 resolve（20 秒超时） | 改为"一次只合成一份，循环到数量达标"，用背包增量判断真实产出 |
| **"缺工作台"识别不到** | 木板做出来了，但工具永远做不出来 | mineflayer 的原文是 `Recipe requires craftingTable`（**驼峰无空格**），早期只匹配 `crafting table`（带空格），自适应回退完全失效 |
| **木制工具被误判为不需工作台** | 做木镐一直卡在"缺工作台" | 木镐其实是 3×3 配方（3 木板在上 + 2 木棍在下），只有木板/木棍/火把/工作台本身是 2×2 |
| 装备悄悄失效 | 放工作台报 `must be holding an item to place` | `bot.equip(item,'hand')` 用了挖矿前取到的旧物品引用（槽位已变）而静默失败；新增 `holdItem()`：按名字重取 → 装备 → **验证 heldItem** → 重试 |
| 多件工具只做出第一件 | "做木镐+木斧"只出镐子，而背包里还有 6 根原木 | 做第一件消耗了木板/木棍，循环做第二件时不补料；改为每件之前按需补木板与木棍 |
| 成功判定依赖错误的信号 | 工具明明做出来了，`ok` 却是 false | `crafted.ok` 基于"本次调用前后该物品的增量"，若物品已在背包则增量为 0；改为**先看背包里有没有** |
| keep-alive 容忍度过低 | 进服一两分钟后莫名掉线（`keepAliveError` / `Timed out`） | minecraft-protocol 默认 30 秒，服务器忙于生成区块时不够；放宽到 90 秒并加进服静置 |
| 每个技能都触发下树冠 | 站在低树枝上也要下地，白白打断当前任务 | 缺少落差门槛；改为只在离地面 ≥3 格时才下降 |
| 文件被 write 工具以外的手段损坏 | `actions.js` 中文全变乱码、语法碎裂 | 用 PowerShell 读写 UTF-8 文件（5.1 默认按 GBK 解码），且非 ASCII 字符在损坏后无法无损还原。**教训：改文件一律用文件工具，不要用 shell 重写内容** |
