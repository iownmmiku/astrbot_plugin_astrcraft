## 三、值得动的（按"收益 ÷ 风险"排序）

### P1　发送量：工具描述 12,742 字符

**为什么值得动**：模型往返的耗时**主要取决于输入大小**（首字延迟随输入增长）。
工具表是输入里最大的一块，而且**每轮都发**。

**风险**：工具描述是模型唯一的说明书，砍了会伤质量 ✗
**所以不能盲砍**。可行的做法（按保守程度）：
1. **合并同类工具**（62 个里有没有功能重叠的？先查）
2. **把"长解释"移到攻略文档**（`skills_docs/`），描述里只留"什么时候用"
   —— 模型需要细节时可以 `mc_load_skill` 去读 ✓
3. **按场景给工具**（探索时不给建造工具）—— 风险最高，最后考虑

**状态**：待量（要先数出"哪几个工具的描述最长、有没有重叠"）

### P2　轮数：MAX_STEPS = 6

**为什么可能值得动**：一次决策最多 6 轮 × 单轮耗时 = 她站着的时长 ✗

**但**：已经在"提交长任务"时**提前结束** ✓ 实际轮数通常 1~3 ✓
**所以要先量**：真实运行里平均几轮？如果平均 1.5 轮，降上限没意义 ✗

**状态**：待量（等那行「决策耗时」日志里的"本轮调了 N 次工具"）

### P3　"动作不流畅"：两次决策之间的空档

**关键问题（还没确认）**：她是在**两次决策之间**站着，还是在**技能执行中**卡着？
这两者的修法完全不同 ✗

- 如果是**决策之间**：空档 = 准备 + 模型往返 ✓ 该动 P1/P2
- 如果是**技能执行中**：该看技能内部的等待
  （`settle` 的固定 delay、走路、挖方块、`humanize` 的停顿）

**已知的技能内部固定等待**：
- `settle()` 每个技能开头都调（含 `delay`）✓ 值不值得省要看实测
- `humanize.maybeIdlePause({chance: 0.06})` —— **故意的**人性化停顿 ✓ 不该动
- `pillarUpOne` 的跳跃轮询 ✓ 必要

**状态**：待量（需要一次真实运行）

### P4　让"思考"和"动作"重叠

**想法**：她执行任务时（几秒到几分钟），下一个决策的**准备工作**
（状态简报 / 生存建议 / 知识库检索）可以**提前算** ✗
但**模型调用不能提前**（状态会变）✓ 所以只能省准备那部分（毫秒级）✗ **收益小** ✓

**结论**：不值得做 ✗

## 五、要往下走需要什么

**一次真实运行的那几行日志**：

```
决策耗时：准备 ___ms（心情 __ms，状态简报 __ms，生存建议 __ms，
        知识库检索 __ms，拼提示词 __ms）+ 模型 ___ms = 共 ___ms；
        提示词 _____ 字符，工具约 62 个，本轮调了 _ 次工具
```

有了它就能确定：
- 模型占比大 → 动 **P1（发送量）**
- 准备占比大 → 查是哪一段（`_brief` 的 RPC？知识库检索？）
- 两者都不大 → 那"慢"在**技能执行**里，动 P3

**没有这个数据就动手，就是在猜** ✗ —— 这轮任务里我已经因为"不量就改"
踩过几次（`pave` 的三次迭代里有一次就是猜错了方向）。
