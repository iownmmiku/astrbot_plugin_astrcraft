# 身体层设计：从"定时器 + 队列"改成"每 tick 竞价"

> 这份文档回答 T5：现在我的实现是 **1 秒反射定时器 + 优先级任务队列**，
> 而真正该做的是**每 tick 竞价的身体层**——本能随时能抢走 LLM 正在做的任务、
> 做完**归还**。
>
> 先写清楚再动手：这是架构级改动，会碰到所有技能的运行方式。

---

## 一、现在是怎么跑的（事实，不是设想）

| 机制 | 现状 | 代码位置 |
|---|---|---|
| 反射层 | **1 秒**一个定时器，纯本地规则 | `bot.js` `_startLoops` → `_reflexTick` |
| MLG | 单独 **100ms** 循环（因为 1 秒会完全错过坠落） | `bot.js` `_mlgTick` |
| 任务队列 | 优先级队列，**可抢占**（`preemptible: true`） | `bot.js` `submitSkill` / `submitAction` |
| 优先级 | CRITICAL(-10) / REFLEX(0) / SURVIVAL(10) / USER(20) / SKILL(30) / AUTONOMY(40) / IDLE(50) | `PRIORITY` |
| 本能 | 10 个分支，各自 `_submitReflex(name, run, level)` | `bot.js` `_reflexTick` |
| LLM | 通过 ActionAgent 调工具；工具提交技能任务 | `action_agent.py` |

**能用的部分**：优先级分层是对的；MLG 单独快循环也是对的（实测必须）。

---

## 二、三个真实缺陷（都有实测证据）

### 缺陷 1：抢占 = 取消，不是挂起 → 被抢的任务**从头再来**

实测：早期"挖困自救"用 `critical` 级，误报时把正在跑的 `mine_ores` **取消了**，
`engine_check` / `crafttest` 跟着挂 ✗ 后来改成 `normal` 级绕开，
但**根本问题没解决**：任何真正的抢占都会让长任务白做。

### 缺陷 2：本能的最坏延迟是 1 秒

反射层 1 秒一次 ✗ 而"错过一秒就必死"的场景（坠落）已经证明必须更快
（所以 MLG 才单独拆到 100ms）✓ **其它本能没有这个待遇**——
被怪贴脸、溺水、着火都可能等满 1 秒。

### 缺陷 3：本能和 LLM 任务在**两套系统**里，没有统一比较

本能走 `_submitReflex`（直接进队列），LLM 走工具 → `submitSkill`（也进队列）✗
两边的"出价"没有在一个地方比较，所以：
- 没法回答"现在到底该谁动"
- 也没法做"本能做完把身体还回去"（因为不知道还回给谁）

## 三、目标设计

### 3.1 每 tick 竞价

```
每 50ms（一个 MC tick）：
  1. 收集所有"想动身体"的诉求：每个本能出一个 (优先级, 能不能执行)
  2. 如果最高出价 > 当前占用者的出价 → 抢占
  3. 抢占：把当前占用者**挂起**（不是取消），记录它"做到哪了"
  4. 本能做完 → **恢复**被挂起的占用者
```

**出价表**（照 numen 的分层，按我的场景调整）：

| 本能 | 出价 | 能被抢吗 | 为什么 |
|---|---|---|---|
| 坠落（MLG） | 10 | ❌ 不能 | 唯一"错过一秒就必死" |
| 溺水换气 | 9 | ❌ 不能 | 也是必死，而且只有十几秒 |
| 岩浆/着火 | 8 | ❌ 不能 | 掉进去就没了 |
| 被怪贴脸（≤3 格） | 7 | ❌ 不能 | 站着挨打等于送死 |
| 低血后撤 | 6 | ❌ 不能 | 同上 |
| 进食 | 5 | ❌ 不能 | 饿死是慢性但确定 |
| 脱困（被埋住） | 4 | ❌ 不能 | 不做就什么都做不了 |
| 反击（远处怪） | 3 | ✅ 能 | 不紧急 |
| LLM 的任务 | 1 | ✅ 能 | **出价最低的竞价者** |
| 捡掉落物 / 插火把 | 0 | ✅ 能 | 只在完全空闲时做（已经这样了 ✓） |

### 3.2 挂起与恢复（最难的一块）

**问题**：技能是普通 async 函数，中间被 await 打断后**没有恢复点** ✗

**三个可选方案**：

| 方案 | 做法 | 代价 | 我的判断 |
|---|---|---|---|
| **A. 只在任务边界抢占** | 技能跑到"一个完整动作结束"才允许被抢 | 本能的延迟变成"最长一个动作"（可能几秒）✗ 违背初衷 | ❌ 不可行 |
| **B. 给技能加 checkpoint** | 每个技能自己声明"怎么从中间恢复" | 要给 16 个技能逐个写恢复逻辑，工作量很大 | ⚠️ 长期正确，短期做不完 |
| **C. 抢占 = 取消 + 技能自己可续建** | 技能被取消后，下次重跑时**跳过已经做完的部分** | 需要技能"幂等 + 可续建" | ✅ **选这个** |

**选 C 的理由**：
- 已经有先例——`blueprint` 就是可续建的（"跳过 N 块（已经是了）"）✓
- 判断标准天然存在：**背包里有没有、目标方块是不是已经放好** ✓
- 不需要改技能签名，只要求"重跑时不白费" ✓

**所以 C 的落地要求**：把"可续建"从 blueprint 推广到所有长技能——
`chop_tree` / `mine_ores` / `mine_stone` / `build_shelter` 重跑时
**先看已经完成了多少**，从那里接着做 ✓（它们大多已经按"数量差"来算了 ✓
比如 `mine_ores` 是 `want = startHave + want` ✓ 天然可续建）

### 3.3 防抖动

抢占本身会抖动（本能反复抢、任务反复重启）✗ 三条防护：

1. **最小占用时间**：抢占后至少跑 `N` 毫秒（默认 300）才允许再抢
2. **抢占冷却**：同一个本能两次抢占之间至少隔 `M` 毫秒（脱困现在是 8 秒 ✓）
3. **抢占次数上限**：一个任务被抢超过 `K` 次（默认 5）→ 如实报告"我被反复打断"
   （而不是无限重启）

## 四、落地顺序（分四步，每步都能独立验证）

| 步 | 做什么 | 怎么验证 | 风险 |
|---|---|---|---|
| **S1** | 把反射层的 1 秒循环改快（目标 200ms；MLG 保持 100ms） | 现有 test_unstuck / test_humanize 全过；测"被怪贴脸时的反应延迟" | ⚠️ **已试过，回退了**（见下） |
| **S2** | 抽出 `_bid(priority, canRun)` 统一入口：本能和技能任务都走它 | 新增 test_bid：出价高的能抢、出价低的不抢 | 低 |
| **S3** | 抢占改成"取消 + 标记可续建"，并给技能加"续建"检查 | 新增 test_resume：被抢的长任务重跑时**不白费**（背包/世界状态接着算） | 中 |
| **S4** | 加防抖动三件套（最小占用、冷却、抢占上限） | 新增 test_thrash：模拟反复抢占，确认不会无限重启、且会如实报告 | 中 |

### S1 的实测结论（已回退，记下来免得再犯）

**"把 1 秒改成 200ms"不是改个数字那么简单。** 我改了之后
`test_unstuck` 的"**完全被埋住时能自救**"**连续 3 次失败**（原来稳定 3/3），
回退到 1 秒后立刻恢复 3/3。

**原因**：脱困逻辑里有一串**按秒调过的时间常数**——
8 秒节流、2 秒二次确认、60 秒降频——反射层快 5 倍之后，
这些常数的**相对关系**变了，行为跟着变（比如"确认一次"的窗口里
多跑了 5 次 tick，中间状态被改了）。

**所以 S1 的正确做法**：把这些时间常数**一起重新调**（按 tick 数而不是秒来算），
并且每调一次都重跑 `test_unstuck`。在那之前默认保持 1 秒。

代码里留了 `MC_REFLEX_MS` 环境变量可以调快，方便做这个实验。

**S2 和 S3 可以先做**（S2 低风险且独立；S3 是核心，需要逐个技能确认可续建）；
**S4 依赖 S3**。S1 放在 S3 之后——因为 S3 做完之后，抢占不再有代价，
那时再把频率提上去、重新调常数，才是安全的。

## 五、不做什么（明确划界）

- **不改技能的调用方式**：技能仍然是 `(actions, nav, ctx, params) → result` ✓
  身体层只在**外面**决定"现在让谁跑"
- **不做线程/进程级隔离**：都在同一个事件循环里，靠 `await` 让出 ✓
- **不追求"零延迟"**：50ms 竞价是目标，做不到就 100ms，**不能回到 1 秒**

---

## 六、这一项和 T2/T4 的关系

- **T2（乱走乱挖）**的根因是"模型微观管理" → 已由 T4（技能承担多步 + 提交即停）解决大半
- **T5** 解决的是另一半：**本能和任务之间的协调**。它不会让"乱走"消失，
  但它能让"本能抢身体"这件事**不把长任务搞白做**（缺陷 1）
- 换句话说：**T5 是"让抢占不再有代价"**，T2/T4 是"少做无意义的事" ✓ 两者互补
